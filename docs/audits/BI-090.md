### BI-090-F02

- **Severity:** medium
- **Category:** correctness
- **Authority:** [`batch-ingestion.md`, Exercise 1](../specification/batch-ingestion.md#exercise-1--rest-api-ingestion), line 163; [`tasks/backlog.yaml`, BI-050 scope](../../tasks/backlog.yaml), line 160.
- **Evidence:** [`api/service.py`](../../src/batch_ingestion/api/service.py) lines 363–375 and 604–612 write only one manifest next to each raw page; [`core-contracts.md`](../contracts/core-contracts.md) line 62 and [`api-ingestion.md`](../ingestion/api-ingestion.md) lines 120–126 explicitly say that schema v1 creates no aggregate run manifest. The `RunSummary` is emitted output, not an immutable persisted manifest.
- **Observed result:** a successful paginated invocation leaves page manifests, potentially retaining earlier physical `run_id` values after recovery, plus an ephemeral final summary. No persisted manifest states that the complete logical run finished.
- **Expected result:** the REST flow persists “a manifest for the complete logical run” in addition to preserving every raw page and avoiding duplicate page writes.
- **Impact:** operators can infer completeness only from page-envelope data and a complete key set; the durable object state has no run-level completion record matching the explicit specification and BI-050 scope.
- **Recommended boundary:** create an ADR before repair because a new manifest cardinality/key contract is architectural; then add an immutable deterministic logical-run manifest, reconciliation rules, tests, and operator documentation without rewriting page manifests.
- **Acceptance impact:** blocking.

### BI-090-F03

- **Severity:** medium
- **Category:** correctness
- **Authority:** [`batch-ingestion.md`, Observable metrics](../specification/batch-ingestion.md#observable-metrics), lines 261–277; [`api-ingestion.md`](../ingestion/api-ingestion.md#structured-output-metrics-and-exit-codes), line 160.
- **Evidence:** [`api/service.py`](../../src/batch_ingestion/api/service.py) lines 386–416 emits the final summary only for its five listed domain exception types; raw boto `ClientError` from `reconcile_payload_manifest` or `write_immutable` bypasses that block. [`files/service.py`](../../src/batch_ingestion/files/service.py), `ingest_file_delivery`, emits only on its success/rejection return and has no failure-summary boundary. [`postgres_snapshot/service.py`](../../src/batch_ingestion/postgres_snapshot/service.py), `ingest_order_snapshot`, emits a failure summary only for `SnapshotHandledError`. Their CLIs catch backend exceptions and emit only generic errors. The bounded API reproduction recorded `events=[]` and `run_summary_count=0` for S3 `ClientError` in `artifacts/audit/BI-090-slice2/static-review.log`.
- **Observed result:** an attempted REST date, file delivery, or PostgreSQL snapshot can terminate on S3 setup/read/write failure without the required source terminal event or `run_summary`.
- **Expected result:** every attempted ingestion emits the final structured summary with stable trace identifiers, including mandatory S3-unavailable failure paths.
- **Impact:** mandatory infrastructure failures lose the counters, duration, logical identity, and terminal event promised to operators; the generic CLI record cannot replace the required summary.
- **Recommended boundary:** normalize backend S3 exceptions at the service boundary, emit the failed event and summary once, preserve exception chaining and stable exit behavior, and add unit plus live S3-unavailable assertions.
- **Acceptance impact:** blocking.

### BI-090-F04

- **Severity:** medium
- **Category:** correctness
- **Authority:** [`AGENTS.md`, reliability/test policy](../../AGENTS.md), lines 66 and 112; [`batch-ingestion.md`, Exercise 1](../specification/batch-ingestion.md#exercise-1--rest-api-ingestion), lines 157–164; [`tasks/backlog.yaml`, BI-050 scope](../../tasks/backlog.yaml), line 159.
- **Evidence:** [`api/fetcher.py`](../../src/batch_ingestion/api/fetcher.py) lines 274–293 asks HTTPX 0.28.1 `Response.iter_raw()` for one chunk as large as the bounded response and checks the total elapsed budget only after that iterator yields. HTTPX documents `iter_raw(chunk_size=...)` as buffering up to the requested chunk size while read timeout limits individual receive inactivity, not complete-response wall time. A deterministic slice-2 stream yielded ten bytes every 0.6 seconds; with `HTTP_MAX_ELAPSED_SECONDS=1`, all ten transport chunks were consumed and elapsed reached 6.0 seconds before the application raised (`artifacts/audit/BI-090-slice2/static-review.log`).
- **Observed result:** a peer that continuously trickles bytes below the per-read timeout can keep one successful response open beyond the configured total elapsed budget; in the limit, that wait has no application-level wall-time bound.
- **Expected result:** request retries and response consumption respect the configured attempt/elapsed bounds, and all waits are bounded.
- **Impact:** the REST command can exceed its documented bounded execution contract indefinitely even though retry counters and phase timeouts are configured.
- **Recommended boundary:** enforce the monotonic deadline while consuming transport-sized chunks (or use an equivalent bounded streaming primitive), retain the byte ceiling, and add a deterministic slow-trickle test proving prompt termination.
- **Acceptance impact:** blocking.

[`check_local_env.py`](../../scripts/check_local_env.py) lines 10–29 and 59–110 validates only infrastructure ports, credentials/placeholders, Garage RPC syntax, and three S3 bounds; [`init_local_env.py`](../../scripts/init_local_env.py) lines 70–75 and 184–190 uses exactly that partial validator before atomic publication. ## Residual limitations

The following are documented contract limits, not findings unless implementation or claims exceed them in later review:

- Garage has no bucket versioning; conditional create is not the immutability foundation.
- One sequential writer owns a logical batch; concurrent-writer safety is not claimed.
- Delivery uses deterministic keys, idempotent writes, and safe redelivery, not exactly-once semantics.
- S3 movement is verified `copy -> verify -> delete`, not atomic rename.
- A PostgreSQL MVCC snapshot does not survive a dead connection; resume revalidates the descriptor and replays from chunk 1.
- JSON file validation may use memory up to the configured byte ceiling; CSV and Parquet are streamed/batched.
- The frozen baseline is a dirty export; later commits or clean-export checks do not reclassify it.
