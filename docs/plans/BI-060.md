# BI-060 implementation plan — file ingestion

Status: complete; slices 1-5 implementation, documentation, acceptance validation, and task closeout are finished

Dependencies: `BI-030` and `BI-040` are complete

Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [ADR 0002](../adr/0002-use-whole-file-atomicity-for-file-ingestion.md), [core contracts](../core-contracts.md), [storage contract](../storage-contract.md), and [source contracts](../source-contracts.md)

## Objective

Implement bounded, restart-safe intake of supplier-price CSV, JSON, and Parquet deliveries. A command stages the exact local bytes under a deterministic landing key, preserves the same bytes under the existing immutable raw-object contract before parsing, validates the complete file, and converges the staged object to exactly one deterministic `archive` or `rejected` disposition.

One delivered file is one acceptance unit. Any required validation failure rejects the whole file, publishes no accepted subset, and retains the original bytes. The implementation claims deterministic keys, immutable/idempotent writes, explicit duplicate classification, and recoverable sequential redelivery. It does not claim an atomic S3 rename, exactly-once delivery, or concurrent-writer safety.

## Existing contracts that must not change

- `BatchIdentity`, `batch_id`, the `raw/...` and `manifests/...` layouts, manifest schema version 1, and `RunSummary` remain unchanged. A change to any existing contract requires an ADR.
- Manifest cardinality remains one manifest for one canonical raw payload. Archive/rejected disposition objects do not receive additional manifests.
- Every delivery is preserved under the canonical raw key before format or row validation. A valid raw payload receives terminal manifest status `succeeded`; an invalid raw payload receives terminal status `rejected`.
- Rejection codes and diagnostics are not added to manifest schema version 1. The durable primary reason is encoded in the rejected disposition key, and bounded details are emitted in the structured terminal event.
- The first terminal manifest retains its `run_id` and `original_file_name`. A redelivery never rewrites that manifest merely to record another physical attempt or filename.
- File modules use the shared storage boundary. They must not call `boto3` directly, trust `ETag` as SHA-256, overwrite a conflict, or perform Garage administration.
- Imports remain side-effect free: no environment read, local-file read, S3 client construction, or S3 request occurs at import time.

ADR 0002 delegates the previously undefined landing/archive/rejected and rejection-diagnostic representation to BI-060. The auxiliary keys below do not replace or relax the existing raw/manifest contract, and no new runtime dependency is required.

## Module and ownership plan

Add `src/batch_ingestion/files/` with narrow responsibilities:

- delivery contracts: strict landing-key construction/parsing, supported source/filename rules, logical identity, canonical payload name, disposition keys, and duplicate classes;
- validators: common supplier-price row rules plus format-specific CSV, JSON, and Parquet readers;
- diagnostics: stable rejection codes, bounded value-free details, deterministic primary-code precedence, and whole-file metric calculation;
- ingestion service: staging handoff, exact-key reconciliation, raw-before-validation ordering, disposition convergence, immutable manifest creation, duplicate handling, and final events/summaries;
- CLI adapter: local file checks, bounded checksum/length calculation, explicit configuration/client lifecycle, `run`/`resume` commands, structured output, and exit codes.

Extend `batch_ingestion.storage` only with generic exact-key operations needed by all source adapters: bounded download to a context-owned seekable spooled file, and read-only exact-object inspection/verification. These operations stay format-agnostic, stream SHA-256 in bounded chunks, close response bodies, and use no prefix listing. File-domain rules and disposition key derivation do not belong in the storage module.

Unit tests use local streams, temporary files, recording storage fakes, and injected clocks. Integration tests use only local Garage and the committed BI-040 fixtures or test-owned malformed payloads.

## Fixed design decisions

### Admission boundary and command inputs

The implemented command forms will be:

```bash
make ingest-file ARGS="run --source supplier-prices --date 2026-09-01 --path /path/to/supplier-prices-2026-09-01.csv"
make ingest-file ARGS="run --source supplier-prices --date 2026-09-01 --path /path/to/file.csv --expected-sha256 <64-lowercase-hex>"
make ingest-file ARGS="resume --landing-key 'landing/file/...'"
```

`run` requires a canonical ISO date, a regular seekable local file, and a basename that already satisfies the existing manifest-safe payload-segment contract. It streams the local file to calculate actual byte length and SHA-256, derives a deterministic landing key, writes that key immutably, and delegates to the same service used by `resume`. The storage boundary re-verifies the local stream during the immutable write, so a file changed between checksum and upload fails visibly instead of publishing mismatched bytes.

`resume` strictly parses one BI-060 landing key. The key contains all non-secret inputs needed to derive the batch, raw key, and candidate dispositions; it works when landing is source-only, both landing and destination exist, or landing has already been deleted. If landing is absent, the service reads the canonical raw object and can reconstruct landing immutably before retrying movement.

Before intake, the CLI rejects an unreadable operating-system path, a non-regular file, a noncanonical date, an invalid expected-checksum token, or a basename that cannot be represented by manifest schema version 1. Those are usage/admission failures and create no S3 state. Once bytes are staged, every business validation failure is retained under raw and rejected keys. “Unreadable file” in ADR 0002 means bytes that the declared CSV/JSON/Parquet parser cannot read; an OS path from which no bytes can be obtained cannot be preserved.

The sole production source allow-list is `supplier-prices`. Any other syntactically valid normalized source can be staged and receives `unsupported_source`; arbitrary unsafe source text is rejected before intake because it cannot form a canonical identity or key.

### File name and format contract

A supplier delivery name must be one manifest-safe basename matching:

```text
supplier-prices[-<label>...]-YYYY-MM-DD.(csv|json|parquet)
```

Each optional label component contains lowercase ASCII letters or digits. The date is the final 10 characters before the extension, must be canonical, and must equal the explicit source date. This accepts the BI-040 same-name files and the `original`/`renamed` pair while still rejecting unrelated or date-mismatched names.

The declared format comes from the lowercase extension. A safe basename with an unsupported extension is staged with format `unknown`, retained, and rejected as `invalid_file_name`; it is never content-sniffed into another format. `csv`, `json`, and `parquet` map to stable content types `text/csv`, `application/json`, and `application/vnd.apache.parquet`. `unknown` uses `application/octet-stream` and canonical payload name `payload.bin`.

### Logical identity and deterministic keys

Create `BatchIdentity(source_type=file)` from the explicit source/date and these sorted logical parameters:

- `content-sha256`: SHA-256 of the exact delivered bytes;
- `declared-format`: `csv`, `json`, `parquet`, or `unknown`;
- `expected-sha256`: the supplied expected checksum or literal `none`;
- `validation-contract`: literal `supplier-prices-v1`.

The actual filename is deliberately excluded. Equal bytes delivered under a different valid name therefore resolve to the same batch and canonical raw payload, allowing renamed-content detection without another business-data copy. Declared format and expected checksum remain in identity because either can change validation outcome for the same bytes. A future validation-contract change must use a new explicit version rather than reinterpret an existing terminal batch.

Canonical raw payload names are `payload.csv`, `payload.json`, `payload.parquet`, or `payload.bin`. They use the existing key functions unchanged:

```text
raw/file/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/{payload_name}
manifests/file/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/{payload_name}.manifest.json
```

BI-060 defines these auxiliary deterministic keys:

```text
landing/file/{source_name}/source_date={YYYY-MM-DD}/format={format}/content_sha256={actual_sha256}/expected_sha256={expected_sha256|none}/{original_file_name}
archive/file/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/{payload_name}
rejected/file/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/reason={rejection_code}/{payload_name}
```

All components are canonical and bounded. Keys contain no local directory, credentials, free-form diagnostic text, or raw field values. Same-name redelivery derives the same landing key; renamed identical content derives a different landing key but the same raw and final disposition keys. Different bytes derive another batch. A conflicting object at any deterministic key is never overwritten.

### Rejection codes and diagnostics

The stable primary rejection codes, in precedence order, are:

1. `unsupported_source`;
2. `invalid_file_name`;
3. `source_date_mismatch`;
4. `checksum_mismatch`;
5. `malformed_file`;
6. `schema_mismatch`;
7. `empty_file`;
8. `missing_required_value`;
9. `invalid_field_type`;
10. `business_rule_violation`;
11. `record_limit_exceeded`.

The first applicable code determines the rejected key. Earlier contract-level failures may stop deeper parsing when the format or source is not trustworthy. For a parseable file, validation continues through the configured record/diagnostic bounds so whole-file counters and useful correction details are available.

The terminal file event contains `outcome`, `rejection_code`, `details`, and `details_truncated` in addition to non-secret `source_date`, `batch_id`, `run_id`, keys, original filename, format, and duplicate class. Each detail contains only a stable code plus optional one-based `record_number` and canonical field name. It does not contain rejected values, complete rows, payload bytes, local absolute paths, or exception representations. Details are ordered by record number, field order, and code and capped by configuration; `details_truncated=true` reports omitted diagnostics.

The rejected object path durably retains the machine-readable primary reason without changing the manifest. Structured output carries bounded detail for the operator. No separate diagnostic sidecar or second manifest is introduced in BI-060.

### Supplier-price schema and row rules

The exact required field order is:

```text
supplier_id, product_id, price_minor_units, currency, effective_date
```

All formats reject missing or extra fields. Required string fields must be non-empty after no implicit trimming or normalization. Accepted values satisfy:

- `supplier_id`: string matching `SUP-[0-9]{3}`;
- `product_id`: string matching `SKU-[0-9]{4}`;
- `price_minor_units`: strict integer, excluding booleans, and greater than zero;
- `currency`: one of `EUR`, `GBP`, or `USD`;
- `effective_date`: a canonical date equal to the command source date.

Validation never rewrites, reorders, normalizes, or reserializes the payload.

Format-specific behavior is fixed:

- CSV decodes UTF-8 strictly, requires the exact header once, rejects malformed column counts, and processes records incrementally with the standard-library CSV reader. Numeric/date strings must already be canonical; surrounding whitespace and signs are not silently normalized.
- JSON decodes UTF-8 strictly, requires one top-level array, exact object keys, and strict JSON value types. Loading is allowed only under the configured maximum file-byte bound, making peak input memory explicit rather than unbounded.
- Parquet opens a seekable verified stream, requires the exact non-null Arrow schema from `docs/source-contracts.md`, and iterates `RecordBatch` values with the configured batch-row limit. It must not call a whole-table read API.

CSV/Parquet processing is batch/row bounded; JSON is byte bounded. Every format also enforces a positive maximum record count and a positive maximum diagnostic count. Malformed parser/library exceptions are converted to `malformed_file` with bounded safe context; programming, storage, and configuration errors are not mislabeled as source rejection.

### Whole-file counters

Metric meanings for BI-060 are:

- `records_read`: records whose boundaries were trustworthy before completion or failure;
- `records_accepted`: `records_read` only when the whole file is valid, otherwise zero;
- `records_rejected`: all `records_read` when a parseable file is rejected, otherwise only the records read before parsing became unsafe;
- `pages_fetched`: always zero;
- `bytes_written`: newly created canonical raw payload bytes only, excluding landing/disposition copies and manifests;
- `retry_count`: always zero because S3 request retries remain owned by bounded Botocore configuration;
- `duplicate_count`: one when a complete existing raw/manifest pair is an understood redelivery, otherwise zero;
- `duration_seconds`: injected monotonic elapsed time for the command.

A mixed three-record fixture reports `records_read=3`, `records_accepted=0`, and `records_rejected=3`. Empty files report all three counters as zero and remain visible through `status=rejected`, `reason=empty_file`, and the terminal event. A schema failure before trustworthy rows reports zero rows. Duplicate valid files are revalidated from preserved bytes and report their record counts plus `duplicate_count=1`; duplicate rejected files retain rejection counters and also report `duplicate_count=1`.

### Duplicate classification

Duplicate classification is separate from validation outcome:

- `new_delivery`: no complete manifest existed before this attempt;
- `same_name_redelivery`: a complete manifest exists and its `original_file_name` equals this delivery name;
- `renamed_content`: a complete manifest exists for the same content identity but records a different original name.

A valid duplicate completes successfully without replacing raw bytes, the archive object, or the original `succeeded` manifest. A rejected duplicate remains a handled rejection and reuses the original `rejected` manifest and rejected object. In both cases the current landing object is still converged to the existing final disposition, and the structured event records the duplicate class.

Manifest status `duplicate` is not used to mutate or replace the first terminal manifest. If an interrupted first attempt left only raw bytes and no manifest, no committed original-name provenance exists; the physical attempt that completes the manifest establishes `original_file_name`.

### Processing and commit order

For one parsed delivery descriptor, the service performs this order:

1. Obtain exact bytes from landing; on resume with landing absent, obtain them from the canonical raw key. Download into a context-owned seekable spooled file using bounded chunks and verify length/SHA-256 from bytes.
2. Reconcile the canonical raw/manifest keys using the expected checksum and length.
3. For `absent`, write and verify raw bytes immutably. For `payload_only`, reuse the verified raw object. For `complete`, strictly validate the file manifest and preserve it. `manifest_only`, malformed manifest, wrong linkage, and byte conflicts fail visibly without cleanup.
4. Validate only after raw bytes are verified. Derive accepted/rejected outcome, primary rejection code, diagnostics, counters, and exact final disposition key.
5. Probe the finite set of alternative archive/rejected keys. Any conflicting terminal disposition fails visibly; BI-060 does not list prefixes or silently choose one.
6. If both landing and expected disposition are absent but raw exists, reconstruct landing immutably from the verified raw stream. Call shared `move_verified()` to converge `source only`, `both identical`, or `destination only` to destination-only. Do not report completion until destination bytes/metadata are verified and landing is confirmed absent.
7. For `absent` or `payload_only`, write one immutable canonical manifest only after disposition completion. Use `succeeded` or `rejected`, `attempt=1`, the current run ID, exact byte metadata, and the admitted original basename.
8. For `complete`, require the existing terminal status to match revalidation. Preserve its original `run_id` and filename; classify the current delivery by filename. A status/outcome mismatch is a conflict, not an automatic repair.
9. Emit one terminal event and one final `RunSummary` for success or handled rejection/failure.

System interruption before the terminal manifest leaves a recoverable `absent` or `payload_only` manifest state. Transient storage/system failures do not write a terminal `failed` manifest that would block safe retry. Terminal manifests are business validation outcomes, not an attempt journal.

### Recovery state matrix

| Observed state | Required rerun behavior |
| --- | --- |
| Landing only | Verify/download, create raw, validate, move, then write manifest |
| Landing + raw, no manifest | Verify both, validate, move, then write only the missing manifest |
| Landing + final disposition, no manifest | Verify identical destination, delete landing through `move_verified`, then write manifest |
| Raw + final disposition, no landing/manifest | `resume` reads raw, treats movement as already complete, then writes manifest |
| Raw only, no landing/manifest | Reconstruct landing from raw, validate, move, then write manifest |
| Complete pair + newly staged identical landing | Revalidate, classify same-name or renamed duplicate, converge landing, write nothing canonical |
| Landing + conflicting final destination | Fail; retain landing and raw evidence, overwrite/delete nothing |
| Manifest only, malformed manifest, wrong linkage, or raw conflict | Fail explicitly; do not invent data or clean up evidence |
| Landing and destination identical after delete failure | Rerun verifies destination, retries delete, and converges to destination-only |
| Neither landing, raw, nor expected disposition | Fail as missing evidence; never fabricate success |

The restart test must inject failure after successful copy and before source deletion, observe both byte-identical objects, and then prove `resume` leaves only the destination with unchanged raw/manifest state.

### Configuration, structured output, and exit codes

Add explicit positive environment bounds for:

- maximum admitted file bytes;
- in-memory spool threshold before temporary-file spill;
- maximum records per file;
- Parquet validation batch rows;
- maximum rejection diagnostic details.

The spool threshold must not exceed the maximum file bytes. Configuration stays typed, redacted, and explicitly loaded. Temporary files are context-owned and closed on success and every failure. Existing S3 total attempts and socket timeouts remain the only request-retry budget.

The file CLI emits newline-delimited structured JSON and uses the existing stable exit-code classes:

- `0`: accepted new delivery or accepted duplicate;
- `2`: CLI/admission error before bytes can enter the canonical contract;
- `3`: invalid configuration;
- `4`: handled file rejection, state conflict, or recoverable ingestion failure;
- `5`: unexpected runtime setup/cleanup failure.

A rejection is observable and retained but still returns non-zero. Events and logs never include payload rows, field values, credentials, full local paths, or exception text that may contain them.

## Non-goals and risks

- No row splitting, normalized output, transformed dataset, schema evolution, XLSX, multipart upload, directory watcher, scheduler, PostgreSQL snapshot work, or concurrent writer coordination.
- No manifest schema change, second manifest, diagnostic sidecar, or mutable attempt journal. A new requirement for persistent detailed diagnostics beyond the reason-bearing key and structured event requires a reviewed contract decision.
- A basename that cannot satisfy the existing manifest-safe segment contract is rejected before intake because schema version 1 cannot record it. Business-invalid but representable filenames are retained and rejected normally.
- Equal bytes with a different declared extension are different logical identities because format changes parsing. Equal bytes/name with a different expected checksum are also different identities because checksum validation outcome can change.
- A terminal manifest records only the first completed delivery filename. Later renamed redelivery is observable in its current event, not by rewriting historical metadata.
- JSON parsing uses memory up to the configured maximum file-byte bound. CSV and Parquet validation are streamed/batched, while the verified spool may spill to local disk.
- Garage has no versioning, and application-level check-then-write is not safe for concurrent writers. BI-060 remains sequential.

## Documentation basis

The Parquet plan uses current Context7 Apache Arrow documentation from `/apache/arrow`:

- `pyarrow.parquet.ParquetFile` exposes file metadata/schema without requiring a whole-table read;
- `ParquetFile.iter_batches(batch_size=...)` yields bounded `RecordBatch` values and is the selected validation path;
- `pq.read_table()` returns a complete Arrow table and is deliberately excluded from BI-060 validation.

CSV and JSON use Python 3.12 standard-library readers under the explicit bounds above. S3 behavior reuses the already documented and integration-tested Boto3/Garage storage contract rather than introducing a file-specific client.
