# BI-091 execution plan — decide the REST logical-run manifest contract

Status: complete; all three slices finished, ADR 0003 accepted, and BI-092 selected with an implementation-ready handoff

Dependency: `BI-090` is complete and finding `BI-090-F02` is final

Authority: [product specification](../specification/batch-ingestion.md), [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [core contracts](../contracts/core-contracts.md), [storage contract](../contracts/storage-contract.md), [REST ingestion contract](../ingestion/api-ingestion.md), and [`BI-090-F02`](../audits/BI-090.md#bi-090-f02)

## Objective

Resolve `BI-090-F02` with one accepted ADR before implementation. The ADR must define durable evidence that one logical REST batch completed, while preserving the existing immutable raw pages and schema-version-1 page manifests.

BI-091 is a decision task, not an implementation task. It may add the ADR, update the ADR index, refine BI-092, and synchronize planning/handoff documentation. It must not change Python, tests, dependencies, object-storage contents, CLI behavior, README behavior claims, or the current page manifest bytes and keys.

The decision must retain the actual delivery claim: deterministic keys, immutable idempotent writes, and safe sequential redelivery. It must not introduce an exactly-once claim or concurrent-writer safety.

## Current contract and failure being resolved

A REST batch currently has:

- one `BatchIdentity` and deterministic `batch_id` for source, date, resource path, and page size;
- raw payloads named `page-0001.json` through the validated final page;
- one schema-version-1 `Manifest` beside each raw page;
- potentially different page-manifest `run_id` values after partial-run recovery;
- one ephemeral final `RunSummary` for each physical attempt;
- no persisted object that states that the complete logical page set succeeded.

The page pairs are valid immutable evidence and must remain unchanged. The gap is cardinality at the logical-batch level: the product specification requires a persisted manifest for the complete logical run, while the current documentation explicitly treats the page set plus an ephemeral summary as sufficient.

The ADR therefore has to distinguish three identities:

1. the logical batch (`batch_id`), which remains unchanged across replay;
2. each immutable page and page manifest, whose deterministic keys already exist;
3. the physical attempt that first commits the aggregate completion record, which may differ from the attempts recorded by individual page manifests.

## Decision questions the ADR must close

The accepted ADR must answer all of these questions without delegating contract choices to BI-092:

- Is the aggregate a separate metadata document or a new form of the existing one-to-one `Manifest`?
- What is its exact cardinality and deterministic key?
- Which identity fields and version namespace does it use?
- How does it link to every required page and to the immutable page-manifest bytes?
- Which facts prove completion, and in what order is completion published?
- Are failed or partial logical attempts persisted at the aggregate key?
- How are absent, complete, malformed, conflicting, and orphaned aggregate states classified?
- How does replay behave when pages came from multiple physical attempts?
- How are pre-BI-092 batches upgraded without rewriting existing evidence?
- What bounded read/write/parser limit applies to the aggregate page inventory?
- Which current metric, event, CLI, and delivery-semantics claims remain unchanged?

## Alternatives to compare

The ADR must compare at least the following bounded alternatives.

| Alternative | Benefit | Blocking problem or consequence |
| --- | --- | --- |
| Keep page manifests plus emitted `RunSummary` | No migration or implementation work | Rejected by `BI-090-F02`: no persisted logical completion record |
| Change schema-version-1 page manifests to carry aggregate state | Reuses one model | Rewrites or forks existing immutable evidence, confuses one-payload cardinality, and affects file/snapshot readers |
| Represent the aggregate as a synthetic raw payload plus ordinary `Manifest` | Reuses current reconciliation | Invents a business payload that does not exist and makes metadata masquerade as raw source data |
| Persist one aggregate per physical `run_id` | Preserves every attempt | Creates unbounded attempt objects, does not converge to one logical completion record, and complicates replay |
| Persist one immutable API-specific aggregate at a deterministic batch key | Preserves page evidence, gives one durable completion record, and converges on replay | Requires a separate strict schema, exact-key reconciliation, and bounded aggregate inspection |

The planned preferred alternative is the final row: a distinct API logical-run manifest schema at one deterministic batch-level key. The ADR author must still test it against every invariant below and record why the alternatives are rejected; the plan itself is not an accepted architectural decision.

## Candidate contract to evaluate in the ADR

### Cardinality and key placement

The preferred contract is exactly:

- `N` immutable raw page objects;
- `N` unchanged schema-version-1 page manifests;
- `1` immutable aggregate manifest only after all `N` page pairs are validated as succeeded.

The proposed aggregate key is:

```text
manifests/api/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/logical-run.manifest.json
```

The key is derived from the existing normalized identity and `batch_id`. It contains neither `run_id` nor a retry number. It is reserved for API batches, is not derived with `manifest_key_for()`, and cannot collide with the allow-listed `page-NNNN.json.manifest.json` keys.

The aggregate is metadata, not a raw source payload. It therefore has no companion raw object and must not be parsed by the existing `Manifest.from_json()` path.

### Separate schema and version namespace

The preferred aggregate is a new strict document type, tentatively `api_logical_run_manifest`, with its own schema version `1`. This does **not** increment or reinterpret the existing raw-payload manifest schema version.

The ADR must freeze exact field names and types. The candidate minimum is:

```text
manifest_type              constant identifying an API logical-run manifest
schema_version             aggregate-schema version, initially 1
source_name                normalized API source
source_type                constant "api"
source_date                canonical YYYY-MM-DD
batch_id                   existing logical batch identifier
identity_parameters        exact normalized resource-path and page-size values
completion_run_id          physical attempt that first published completion
completed_at               timezone-aware UTC completion instant
status                     terminal aggregate status
page_count                 positive count of required pages
record_count               non-negative validated total record count
pages                      ordered page-evidence entries 1..page_count
```

Each page-evidence entry should contain enough immutable facts to identify and verify the exact evidence without prefix inference:

```text
page_number
object_key
page_manifest_key
payload_content_length
payload_checksum_sha256
page_manifest_checksum_sha256
record_count
```

The ADR must decide the final spelling and whether any field is redundant. It must not omit the raw checksum, page-manifest key, page-manifest checksum, or ordered page number unless it selects and documents an equally exact bounded linkage mechanism.

Serialization should remain compact UTF-8 JSON with sorted object keys and pages in strictly increasing order. Unknown, missing, duplicate, out-of-order, or noncanonical values must be rejected.

Because `HTTP_MAX_PAGES` permits up to 9,999 entries, the ADR must set a finite aggregate-byte bound rather than reuse the 64 KiB page-manifest assumption. The preferred implementation boundary is a fixed conservative maximum of 8 MiB, validated against the two allow-listed source/key layouts and the 9,999-page ceiling. BI-092 must verify both declared and actual bytes before parsing and must not trust `Content-Length` alone.

### Completion and publication order

The preferred completion predicate is all of the following:

1. strict pagination reached the validated final page;
2. the observed page numbers are exactly `1..page_count` with no gap or duplicate;
3. page totals and item counts agree with `record_count`;
4. every raw page matches its expected key, length, and SHA-256;
5. every page manifest is strict schema version 1, has status `succeeded`, links to that raw page, and matches the same source/date/batch;
6. the ordered page inventory has been constructed within the aggregate bound;
7. the aggregate object is immutably created and byte-verified, or an existing identical valid aggregate is reconciled.

Only after aggregate persistence/reconciliation may the service emit its terminal success event and final `RunSummary`. A stop after the final page manifest but before the aggregate deliberately leaves a recoverable incomplete logical batch.

The aggregate records `completion_run_id`, not a claim that every page was created by that attempt. Each page manifest retains its original `run_id`; the ordered page evidence, including each page-manifest checksum, binds the aggregate to the actual mixed-attempt evidence.

### Terminal and failure semantics

The preferred schema-version-1 aggregate has one persisted terminal status: `succeeded`.

Partial, failed, or interrupted attempts do not write a failed object at the deterministic aggregate key. Doing so would make an immutable failure block later recovery to success. Those attempts remain visible through retained page/page-manifest evidence and terminal events/summaries. The ADR must explicitly reject mutable status transitions and unbounded per-attempt aggregate objects.

Logical state is classified by reconciliation rather than by mutating the aggregate:

| Observed state | Meaning and required behavior |
| --- | --- |
| Aggregate absent, page set incomplete or failed | Incomplete/failed logical batch; retain evidence and do not claim completion |
| Aggregate absent, all required page pairs succeeded | Eligible for one immutable aggregate write |
| Aggregate present and all exact evidence matches | Complete; reuse without rewriting its completion run/time |
| Aggregate present but malformed, oversized, unsupported, or wrong-identity | Corrupt/conflicting state; fail visibly and do not replace/delete it |
| Aggregate references a missing, failed, or mismatched page pair | Orphaned/conflicting completion claim; fail visibly and retain all evidence |
| Aggregate write had an uncertain outcome | On rerun, inspect the deterministic key; reuse an identical valid object or report conflict |

Reconciliation uses only the aggregate key and the exact page keys implied by its validated `1..page_count` inventory. Prefix listing must not become the correctness foundation.

### Replay and compatibility

The preferred compatibility rules are:

- existing raw pages and schema-version-1 page manifests remain byte-for-byte unchanged;
- no BI-091 migration, storage write, eager backfill, or compatibility shim is run;
- after BI-092, replay of a pre-aggregate successful batch validates/reuses existing page evidence and creates only the missing aggregate;
- replay of a complete aggregate validates and reuses it, while the current physical attempt still emits its own event and summary;
- replay never rewrites `completion_run_id`, `completed_at`, page manifests, or raw pages;
- failed page manifests remain terminal and cannot be upgraded in place;
- existing readers that address exact page-manifest keys continue to work; inventory/demo readers that assert the complete manifest set are updated only in BI-092;
- normal ingestion continues to fetch and verify source pages as it does today; the aggregate is not an offline substitute for the source;
- no exactly-once or concurrent-writer claim is added.

## BI-092 refinement required at decision closeout

After the ADR is accepted, BI-091 must refine BI-092 so implementation scope follows the selected contract exactly. At minimum BI-092 must name:

- the new aggregate model/parser and deterministic key helper;
- the bounded exact-key storage inspection needed for aggregate and page-manifest bytes;
- aggregate creation after the last succeeded page and before terminal success output;
- reconciliation outcomes and stable error classifications;
- pre-aggregate replay and uncertain-write recovery;
- unit tests for schema, canonical serialization, key determinism, page ordering/linkage, byte bounds, and every state-table row;
- Garage integration for absent aggregate, successful creation, complete replay, post-pages/pre-aggregate interruption, conflict/corruption, and legacy page-only upgrade;
- backfill behavior, exact inventory/demo inspection, API operator documentation, and compatibility wording;
- unchanged page bytes/manifests, raw-only `bytes_written` meaning, sequential-writer limitation, and no exactly-once claim.

BI-092 must remain the first task allowed to change runtime behavior or tests. BI-091 must not pre-create implementation modules or executable fixtures.

## Non-goals and risks

- No aggregate implementation, test implementation, storage write, data migration, CLI option, dependency, configuration setting, or demo behavior change.
- No changes to raw page keys, page manifest keys, schema-version-1 page manifests, `batch_id`, or `run_id` generation.
- No persisted failed aggregate at the deterministic completion key and no mutable aggregate transition.
- No prefix listing as the source of completeness; exact keys and verified bytes remain authoritative.
- No coordination or safety claim for concurrent writers.
- No exactly-once claim and no attempt to persist every physical run.
- The aggregate page list can exceed the existing 64 KiB manifest read limit; the ADR must set a distinct finite bound and BI-092 must enforce it.
- An accepted ADR before BI-092 creates a temporary documented decision/implementation gap. Current-behavior guides must continue to describe page-only behavior until implementation lands.
