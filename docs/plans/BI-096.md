## Fixed evidence boundary

### 1. Name an immutable commit, not a branch or mutable working tree

The attested identifier is one full commit object ID, recorded together with its tree object ID, commit timestamp, subject, and any containing branch or tag names as informational metadata only. Commands must dereference and use the full commit ID; `HEAD`, `main`, a tag, or a short hash is not the evidence identity.

Create a temporary detached Git worktree directly from that commit. Do not use `cp`, `rsync`, `git ls-files --others`, a dirty archive, or the developer worktree as the source. Before setup or validation, require all of the following inside the detached checkout:

- `git rev-parse HEAD` equals the selected full commit ID;
- `git status --porcelain=v1 --untracked-files=all` emits zero bytes;
- both index and worktree diffs are empty;
- the checkout is detached from a mutable branch;
- the commit and tree inventories can be enumerated without an unsafe path or submodule dependency.

Any non-empty status, missing commit, checkout mismatch, unsafe inventory, or required-path omission is a failed attestation. Do not repair the candidate checkout, copy a missing file into it, or silently select working-tree content.

### 2. Record an exact reconstructible source inventory

Record the commit tree ID, tracked-path count, and SHA-256 of a NUL-safe canonical inventory containing each path's mode, Git object type, blob/object ID, and path. Retain the complete inventory under ignored `artifacts/audit/BI-096/`; put its digest and count in the committed report.

The source-closure table in `docs/audits/BI-096.md` must explicitly verify every F01 path that was absent from the frozen baseline, grouped as:

- PostgreSQL snapshot CLI/service and their unit/integration tests;
- demo, failpoint, inventory, worker, local-environment, and clean-export scripts;
- clean-export, demo-contract, and recovery integration tests;
- PostgreSQL snapshot and recovery operator documents;
- the BI-080 and BI-090 plans required to reconstruct the accepted implementation and audit boundary.

Existence is necessary but not sufficient: repository gates and runtime acceptance establish that the committed versions form a usable source set. The report must not claim that their current blobs equal the historical dirty-worktree hashes because later accepted maintenance legitimately changed parts of the source set.

### 3. Separate attestation evidence from source and historical audit state

Create `docs/audits/BI-096.md` only after the candidate revision and detached-checkout provenance are frozen. Generated command logs, inventories, environment files, and timing data belong below ignored `artifacts/audit/BI-096/` and are not copied into the candidate checkout.

## Non-goals and risks

- No product repair, source refactor, test rewrite, dependency update, ADR, manifest/key change, new demo, Possible extension, or stronger delivery guarantee.
- No claim that a local commit is published to an external remote; this repository currently has no configured remote, and BI-096 attests local clean-commit reproducibility only.
- No retroactive PASS for the BI-090 frozen baseline. The later attestation is additional evidence for a different revision.
- No use of the current developer worktree as runtime source, even if its status happens to be clean at execution time.
- No broad Docker cleanup, image prune, default-project reset, or deletion based only on a prefix that was not proven task-owned.
- A missing Docker daemon, image/build failure, cleanup failure, protected-fingerprint change, or source-status drift is visible `blocked`/`fail` evidence, not a reason to reuse mutable services.
- The clean-export harness validates exact inventory before cleanup and reports only a compact final summary. The BI-096 report must pair that result with the committed assertion contract and retained command log so “exact inspection” is not reduced to an unexplained exit code.
- BI-096 was the last authorized backlog task. The project owner's terminal-state decision permits `active_task_id: null` only while every recorded task is done; future work requires a newly authorized atomic task.
