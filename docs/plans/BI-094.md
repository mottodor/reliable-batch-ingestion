# BI-094 implementation plan — REST total response deadline

Status: done; slices 1 and 2 are implemented and accepted

Dependencies: `BI-090` is complete; `BI-092` and `BI-093` are complete prerequisites for the current REST aggregate and terminal-output behavior; [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md) and [ADR 0003](../adr/0003-persist-rest-logical-run-manifest.md) remain binding

Authority: [product specification](../specification/batch-ingestion.md), [REST ingestion contract](../ingestion/api-ingestion.md), [`BI-090-F04`](../audits/BI-090.md#bi-090-f04), and the canonical BI-094 scope and acceptance criteria in [`tasks/backlog.yaml`](../../tasks/backlog.yaml)

## Objective

Close `BI-090-F04` by making `HTTP_MAX_ELAPSED_SECONDS` cover successful-response body consumption as well as request attempts and retry delays. A peer that repeatedly supplies small bytes before the HTTPX read timeout expires must not keep one page fetch alive indefinitely.

The repair must expose each underlying HTTP transport chunk to the existing monotonic budget checks, stop at the first observed expiry, close the response and context-owned spool, and return the existing handled `http_retry_exhausted` outcome. No partial response body may reach S3. Normal HTTP 200 bodies still use exact raw bytes, SHA-256, and the configured byte ceiling before raw-before-parse persistence.

BI-094 changes no configuration names/defaults, retry policy, API identity, object key, page or aggregate manifest schema, metric meaning, CLI exit, storage behavior, or delivery guarantee. It requires no ADR or dependency change.

## Reproduced planning-baseline gap

The current `fetch_page()` creates one `RetryBudget` for the page and clips HTTPX operation timeouts to the initially remaining budget. `_read_success_response()` then calls:

```text
response.iter_raw(chunk_size=min(DEFAULT_CHUNK_SIZE, max_response_bytes + 1))
```

HTTPX 0.28.1 feeds raw transport chunks through a `ByteChunker`. When an integer `chunk_size` is supplied, `ByteChunker` buffers transport chunks until that requested size is available or the response ends. The application therefore cannot run its post-chunk monotonic check while small transport chunks are still being accumulated. A deterministic stream can advance by 0.6 seconds for each one-byte transport chunk under a 1-second total budget and still make the application consume every byte before the buffered iterator yields once.

The per-operation read timeout does not close this gap: HTTPX defines it as the maximum wait for the next response-data chunk, not a wall-clock limit for the complete response. A peer can continuously reset that inactivity boundary by trickling bytes.

## Contracts that must not change

- `HTTP_MAX_ELAPSED_SECONDS` remains one monotonic budget per page across attempts, retry delays, response headers, and the complete successful body.
- HTTPX retains explicit connect/read/write/pool timeouts, and each request still receives timeouts clipped to the budget remaining when that attempt starts.
- The response byte ceiling remains based on exact raw bytes. The first transport chunk that would cross the ceiling fails with `ResponseSizeLimitError`; no truncated body is returned.
- Successful raw response bytes are neither decoded nor reserialized by the fetcher. Content type, byte length, and SHA-256 semantics remain unchanged.
- A deadline reached during an HTTP 200 body remains `HttpRetryExhausted` with `RetryClassification.TRANSPORT_ERROR`, attempt-derived `retry_count`, source-level `http_retry_exhausted`, handled CLI exit `4`, one failed `api_ingestion` event, and one following `run_summary`.
- Once an HTTP 200 body has started, deadline failure does not retry that partial body. The context-owned spool is discarded and closed, so no incomplete page is passed to raw persistence.
- Existing 429/5xx retry behavior, valid `Retry-After`, permanent-4xx handling, malformed-HTTP-200 preservation, raw-before-parse ordering, page reconciliation, ADR 0003 aggregate publication, and backfill fail-fast behavior remain unchanged.
- The public synchronous HTTPX client boundary and environment configuration stay unchanged. No public slow-response fault mode is added to the mock API.

## Fixed implementation design

### 1. Consume unbuffered transport chunks

Change the successful-response loop to consume `response.iter_raw(chunk_size=None)` explicitly. Under HTTPX 0.28.1 this bypasses fixed-size `ByteChunker` accumulation and yields each non-empty raw chunk supplied by the synchronous transport.

Use an explicit iterator loop rather than relying only on the `for` statement:

1. check that the monotonic budget is still positive before asking for the next transport chunk;
2. request the next raw chunk;
3. on normal end-of-stream, check the budget once more before accepting completion;
4. immediately after every returned transport chunk, check the budget again before writing the chunk to the spool or digest;
5. enforce the exact response-size ceiling, then write and hash the chunk;
6. repeat until clean bounded completion.

The pre-read check prevents a new receive operation from starting after known expiry. The post-read check catches the first chunk whose receive crosses the deadline and ensures that crossing chunk is not admitted into the preservable page. A silent peer remains bounded by the existing HTTPX read timeout; a trickling peer is observed after every transport yield and cannot hide behind application-level chunk buffering.

A small private deadline guard may centralize construction of the existing `HttpRetryExhausted` value. It must not introduce a new exception, error code, retry event, clock, timer thread, signal, or async client.

### 2. Preserve cleanup and ownership

`client.stream(...)` remains the response owner and closes the response when deadline failure leaves the context. `_read_success_response()` remains the spool owner until it returns a `FetchedPage`; its existing `BaseException` cleanup closes the spool on deadline, size, protocol, transport, or unexpected failure.

The fetcher returns no `FetchedPage` on expiry. Consequently the service cannot call reconciliation or immutable raw write for that response. Any bytes already written to the local spool from earlier in-budget chunks are temporary process-local evidence only and are discarded on close.

### 3. Keep the existing handled outcome

Do not add a dedicated deadline error code. Raise the existing `HttpRetryExhausted` with:

- `classification = transport_error`;
- `status_code = null`;
- the current HTTP attempt;
- `retry_count = attempt - 1`.

The existing REST service mapping must emit exactly one failed `api_ingestion` event followed by one `run_summary`. For a first-attempt slow HTTP 200 failure before persistence, expected confirmed metrics are zero pages, records, duplicates, and raw bytes; no retry event is emitted merely because a successful response body exceeded its deadline.

### 4. Deterministic test seam

Use a custom in-memory `httpx.SyncByteStream`, `httpx.MockTransport`, and an injected fake monotonic clock. Each stream iteration advances the fake clock before yielding one small byte. Tests use no real sleep, socket, public network, or timing tolerance.

The principal regression uses ten one-byte transport chunks, a 0.6-second clock advance per chunk, and a 1-second total budget. It must prove that only the chunks needed to observe expiry are requested, rather than all ten being buffered and consumed. A patched private spool factory or equivalent internal seam records that the spool closes on failure. The transport stream must also report closed.

Separate service-level coverage proves the stable terminal outcome and absence of storage mutation. Existing normal-response, response-size, 429, retry-budget, malformed-body, service, backfill, CLI, and live API suites provide regression coverage; no arbitrary-sleep slow HTTP integration server is required.

## Non-goals and risks

- No new response deadline setting, timer service, thread, signal, async HTTP client, transport retry, runtime dependency, or mock-source fault endpoint.
- No change to HTTPX's read-timeout meaning. The read timeout still bounds inactivity for one receive; the application monotonic budget bounds the page and is checked around every exposed transport receive.
- No retry of a partially consumed successful body. Retrying after unknown partial source progress would alter existing behavior and is unnecessary because no raw page has been committed.
- No persistence of partial spool bytes for diagnosis. The raw-preservation invariant starts only after a complete bounded HTTP 200 body exists; incomplete response fragments are not valid source payload objects.
- No change to malformed complete HTTP 200 handling: a complete in-budget malformed body is still preserved before parsing and gets its existing failed page manifest.
- No BI-095 full-configuration preflight work or BI-096 clean-commit attestation.
- The synchronous implementation observes expiry immediately before and after transport yields; it does not asynchronously cancel a receive in the middle of a blocking HTTPX call. A fully silent receive remains bounded by the already configured HTTPX read timeout.

## Documentation basis

Planning checked current HTTPX 0.28.1 documentation through Context7 library `/encode/httpx/0.28.1` and the locked installed source. HTTPX documents read timeout as the maximum wait for a response-data chunk, not a whole-response wall-clock timeout. Its `Response.iter_raw()` uses `ByteChunker`: `chunk_size=None` returns each non-empty transport chunk directly, while an integer size buffers transport chunks until that size or end-of-stream. The fixed implementation therefore removes application-level buffering and applies the existing monotonic budget at the transport-yield boundary. No new dependency or ADR is required.
