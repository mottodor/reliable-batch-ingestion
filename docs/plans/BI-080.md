# BI-080 implementation plan — recovery demos and final documentation

Status: complete; all four slices and acceptance validation passed

Dependencies: `BI-050`, `BI-060`, and `BI-070` are complete

Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [ADR 0002](../adr/0002-use-whole-file-atomicity-for-file-ingestion.md), [core contracts](../contracts/core-contracts.md), [storage contract](../contracts/storage-contract.md), and the three source-specific ingestion documents under [`docs/ingestion/`](../ingestion/)

## Objective

Turn the already tested REST, file, and PostgreSQL recovery behavior into bounded operator-facing demonstrations that run from a clean repository export. Implement the four Make targets named by the product specification, add an explicit scenario runner for every mandatory failure, retain inspectable S3 evidence at each interruption boundary, recover only through the existing ingestion primitives, and produce a final read-only inventory proving raw-byte immutability and idempotent replay.

BI-080 is orchestration, fault demonstration, verification, and documentation work. It must not create a second ingestion implementation or weaken the production contracts to make a demo convenient. Production CLIs remain free of fault flags. Demo-only workers may inject faults through existing dependency seams and may deliberately terminate their own process; the subsequent recovery step must use the normal `make ingest-api`, `make ingest-file`, or `make ingest-postgres` path.

The implementation claims deterministic keys, immutable/idempotent sequential writes, bounded retries, safe redelivery, and reproducible recovery. It does not claim exactly-once delivery, atomic S3 rename, persistent PostgreSQL snapshots after disconnect, or concurrent-writer safety.

## Existing contracts that must not change

- `BatchIdentity`, deterministic raw/manifest keys, manifest schema version 1, one-manifest-per-payload cardinality, and `RunSummary` remain unchanged. Any change requires a separate reviewed ADR.
- Raw payloads are never rewritten or deleted merely to reset a demo. Failed and rejected evidence remains visible until an explicitly isolated demo project is destroyed.
- File demos retain whole-file atomicity from ADR 0002. A mixed or schema-invalid file publishes no accepted subset.
- Domain modules continue to access storage only through the shared S3 boundary. Demo inspection may list prefixes through the standard S3 API, but prefix listing must not become an ingestion reconciliation decision.
- Existing API, file, and snapshot CLIs remain the operator recovery commands. Demo orchestration must call or supervise those paths rather than reimplement identity, parsing, serialization, persistence, or resume rules.
- Fault selectors and failpoints are lab-only. They must not be accepted by production CLI argument parsers, loaded by `AppConfig`, written to manifests, or enabled implicitly by environment configuration.
- Every wait, subprocess, retry, and service-readiness check is bounded. A demo must fail non-zero with a structured, secret-free result instead of hanging.
- Imports remain side-effect free. No Docker, network, PostgreSQL, S3, environment, or file mutation occurs merely by importing a demo module.

No new ADR or runtime dependency is planned.

## Ownership and file plan

Add narrow tooling outside the domain packages:

- `scripts/init_local_env.py` — explicit, redacting initialization of an ignored local `.env` from `.env.example`;
- `scripts/demo.py` — parent scenario runner, timeout supervisor, normal-command adapter, inventory verifier, artifact writer, and final demo-summary emitter;
- `scripts/demo_worker.py` — child process used only for deliberate failpoints that must simulate process death;
- `scripts/demo_faults.py` — allow-listed demo-only storage/client/event wrappers; no production module imports this file;
- `tests/unit/test_demo_contract.py` — command registry, timeout, redaction, environment initialization, Make wiring, report, and failpoint contract tests;
- `tests/integration/test_recovery_demos.py` — focused local Compose evidence for the four public targets and mandatory recovery boundaries;
- `scripts/check_clean_export.py` — bounded clean-export walkthrough using only repository-owned, non-ignored files and an isolated Compose project;
- `docs/ingestion/recovery-demos.md` — exact setup, commands, expected intermediate states, recovery commands, artifacts, timing, cleanup, and limitations.

The exact split may be reduced if one file remains small, but domain ingestion code must not absorb demo orchestration. Shared test utilities may be extracted only when they do not create a new runtime abstraction.

Generated reports live below ignored `artifacts/demo/`. They contain NDJSON events, deterministic object keys, lengths, SHA-256 values, manifest statuses, command exit classes, and elapsed time. They contain no credentials, DSNs, Authorization headers, raw rows, complete payloads, environment dumps, backend exception representations, or absolute local paths.

## Fixed command surface

The product-specification targets will exist exactly as follows:

```bash
make demo-happy-path
make demo-duplicate
make demo-api-retry
make demo-bad-file
```

Add two supporting targets:

```bash
make demo-recovery SCENARIO=<allow-listed-scenario>
make demo-inspect
```

`demo-recovery` accepts only the scenario names defined in the mandatory matrix below. Missing or unknown values fail before clients or subprocesses are created and print the accepted names. `demo-inspect` is read-only and verifies the known demo batches from their recorded descriptors; it does not scan the bucket and infer success from arbitrary objects.

All targets run `check-local-env` first, use `COMPOSE_ENV_FILE`, `COMPOSE_PROJECT_NAME`, and the existing bounded configuration, and accept a positive `DEMO_TIMEOUT_SECONDS` Make variable with a conservative default. They emit compact NDJSON and write the same events to a timestamped artifact directory. Human-readable headings go to stderr so stdout remains machine-parseable.

A successful scenario emits:

1. the unchanged source-specific ingestion events and `RunSummary` objects;
2. a `demo_state` event after every expected intermediate/final state assertion;
3. one terminal `demo_summary` containing scenario name, `passed=true`, elapsed seconds, attempted/recovery exit classes, object counts, and artifact-relative report path.

A failed scenario emits one `demo_summary` with `passed=false` and a stable demo error code, then exits non-zero. This wrapper does not replace or modify the existing `RunSummary` schema.

## Local environment initialization and clean-start boundary

The documented clean-start flow will be:

```bash
cp .env.example .env
make init-local-env
make up
make seed SOURCE_SEED=20260901
make demo-happy-path
make demo-duplicate
make demo-api-retry
make demo-bad-file
make test
make down
```

`init-local-env` is explicit and safe to rerun:

- it reads only `.env.example` and the ignored target path selected by `COMPOSE_ENV_FILE`;
- it replaces only recognized `change-me` placeholders with cryptographically random local-only PostgreSQL, Garage RPC, and S3 credential values;
- it writes the target atomically with owner-only permissions and never prints generated values;
- it refuses symlinks, unknown placeholder forms, duplicate assignments, a tracked destination, or overwriting a non-placeholder credential;
- a fully initialized valid file is left byte-for-byte unchanged;
- it runs the existing redacting local preflight before reporting success.

The helper does not silently run from `make up`, rotate an existing environment, or store credentials under `artifacts/`. Manual environment setup remains supported.

The four public demos are repeatable. On a new isolated project they show creation; on a project containing the same complete batches they verify replay and report zero new canonical raw bytes. They never delete a matching developer batch to manufacture a first-run result.

## Public demonstration behavior

### `demo-happy-path`

Run all three production paths for the default source date:

1. REST `fx-rates` ingestion;
2. one valid supplier CSV delivery from the committed canonical-name fixture;
3. one bounded `orders` PostgreSQL snapshot.

Verify exact raw/manifest pairing, succeeded manifests, archived file bytes, PostgreSQL Parquet schema/rows, payload SHA-256 values, and source-specific summaries. Record the snapshot descriptor needed for later resume. The target succeeds both when it creates the clean-project objects and when every matching object is already complete and unchanged.

The measured ingestion portion, excluding first-time dependency installation and image download, receives a three-minute acceptance budget on the validation workstation. The subprocess timeout remains slightly larger and fails visibly rather than weakening that measured requirement.

### `demo-duplicate`

Require or establish the happy-path baseline, capture an exact key/length/checksum/manifest-byte inventory, and then exercise:

- repeated API ingestion;
- repeated snapshot ingestion with the same descriptor and chunk size;
- same-name supplier redelivery;
- byte-identical supplier content under the committed renamed filename.

After replay, require the same canonical inventory and original manifest bytes/run IDs, `bytes_written=0` for canonical raw payloads, expected duplicate counters/classes, no landing objects, and no second business-data copy. Temporary staging is allowed only while the command is running.

### `demo-api-retry`

Reset one unique mock fault key, execute `rate_limit_once`, and prove one 429 body is not persisted, the valid `Retry-After` delay is selected within the configured budget, exactly one retry is reported, and final page pairs succeed. Use a source date/page-size identity that does not collide with the happy-path demo.

### `demo-bad-file`

Copy committed schema-invalid bytes to a canonical supplier filename in the ignored artifact input directory and run the normal file CLI. Also create one bounded malformed UTF-8 CSV for the demonstration requirement that malformed input is inspectable. For each input require the expected non-zero handled exit, exact immutable bytes under raw and one reason-bearing rejected key, one rejected manifest, no archive object, no accepted subset, and a structured rejection summary. Then ingest corrected valid content as a new content identity without deleting the rejected evidence.

## Mandatory failure and recovery matrix

Every scenario records pre-fault state, the exact intermediate state, the normal recovery command, final state, and elapsed time. Expected failure commands are treated as expected only when their stable exit/error code and object state match.

| `SCENARIO` | Injection and expected state | Normal recovery command/evidence |
| --- | --- | --- |
| `api-rate-limit` | Mock API returns `429` once; no 429 body is stored | Same API operation completes inside retry budgets; this is also `demo-api-retry` |
| `api-permanent-500` | Mock API returns 500 through the exact attempt budget; earlier pages may be complete and the failed page is absent | Clear the mock fault and rerun the same `make ingest-api` command; completed pages remain byte-identical |
| `api-malformed-json` | HTTP 200 malformed bytes are retained with one `failed` manifest | Rerun the same command to prove the terminal evidence is re-surfaced unchanged; a corrected upstream body must use a reviewed new logical identity/date and must not overwrite this batch |
| `api-after-page` | Demo worker terminates after page 1 emits completion; page 1 is complete and later pages are absent | Rerun the same production API command with the same page size; page 1 is reused and remaining pages complete |
| `file-same-name` | Complete valid file is delivered under the original name | Repeat normal `make ingest-file ... run`; one canonical raw/archive/manifest remains and classification is `same_name_redelivery` |
| `file-renamed-content` | Identical bytes are delivered under the committed renamed filename | Run normal file intake for the renamed path; classification is `renamed_content` and no second canonical business payload appears |
| `file-schema-invalid` | Exact bytes are retained under raw/rejected with `reason=schema_mismatch` and no accepted rows | Correct and redeliver the complete file through normal `make ingest-file`; corrected bytes create a new content identity while rejected evidence remains |
| `file-during-move` | Demo worker terminates immediately before landing deletion, after verified copy; landing and final destination contain identical bytes, raw is present, manifest is absent | Run normal `make ingest-file ... resume` with the recorded landing key; movement converges to destination-only and the manifest is written last |
| `postgres-connection-drop` | A second connection terminates the reader backend after the first complete chunk; earlier chunk pair remains and no checkpoint/failed manifest appears | Run normal `make ingest-postgres ... resume` with every emitted descriptor field and the same chunk size; replay begins at chunk 1 |
| `s3-unavailable` | A child command receives a bounded unreachable loopback endpoint; no unrelated service is stopped and prior inventory cannot change | Rerun the same normal command with the real `.env` endpoint; retained/absent state reconciles normally |
| `payload-before-manifest` | Demo-only storage wrapper terminates its child process immediately before the first manifest write, after verified raw upload; exact `payload_only` state remains | Rerun the corresponding normal production command; only the missing manifest is added for that payload |

The nine mandatory specification failures map to the table as follows: 429, permanent 500, malformed JSON, same-name file, renamed content, schema violation, PostgreSQL connection drop, S3 unavailability, and payload-before-manifest interruption. `api-after-page` and `file-during-move` provide the additional deliberate process boundaries required by Exercise 5.

Malformed JSON is intentionally a terminal immutable batch, not silently repaired in place. Its “recovery” exercise proves safe re-surfacing and documents that corrected content needs a new reviewed logical identity; no command may delete or overwrite the retained failed payload.

## Deliberate process-failure mechanism

Failures at process boundaries run in `scripts/demo_worker.py`, never in the parent supervisor or production CLI parser. The parent passes one allow-listed scenario and a private artifact/report path, starts the child with a bounded timeout, and expects a dedicated non-zero exit code.

The worker may use only these existing seams:

- API `event_sink` to terminate after a complete page;
- snapshot `event_sink` plus a second Psycopg connection to terminate the active backend after a complete chunk;
- a demo-only S3 client proxy that terminates before `DeleteObject` after verified copy;
- a demo-only storage proxy that terminates before writing a manifest after the payload write has returned successfully.

The worker exits at the boundary without cleanup to model abrupt death. The parent then opens fresh clients, verifies the exact S3 state, and invokes the normal recovery command. Failpoints are one-shot per child process, cannot be selected by arbitrary dotted names, and cannot intercept raw verification, checksum calculation, or conflict checks.

Unit tests use fakes to prove each failpoint fires only after its prerequisite event and never on an unrelated key. Live tests prove actual child-process termination and retained Garage state.

## Inventory, evidence, and cleanup

For every known demo batch, inventory verification records:

- exact raw, manifest, landing, archive, and rejected keys expected for that scenario;
- object length and independently streamed SHA-256, never `ETag` as checksum;
- strict parsed manifest status/linkage/checksum/length and original manifest bytes where replay stability matters;
- snapshot Parquet schema, row count/order, and descriptor bounds;
- absence of forbidden alternative dispositions and unexpected keys under the exact deterministic batch prefixes.

The inspector lists only calculated prefixes and compares the result to an exact expected set. It is read-only and cannot delete, copy, repair, or infer a checkpoint.

Normal public demos preserve evidence and leave services/data available for inspection until `make down`. Integration tests and the clean-export harness use a unique Compose project, ports, bucket, credentials, scenario keys, source identities, and artifact directory. Their `finally` cleanup removes only test-owned objects/rows and then explicitly destroys only the isolated project volumes with the existing exact confirmation contract. Default-project volume fingerprints are compared before and after isolated validation.

## Clean-export walkthrough

`check_clean_export.py` validates that the repository, rather than a developer session, is the source of truth:

1. Create a temporary export from the files reported by `git ls-files --cached --others --exclude-standard`; do not copy `.env`, `.venv`, caches, ignored artifacts, or Docker volumes.
2. Assert that the export contains no local configuration or generated credentials.
3. Create an isolated ignored `.env` through `init-local-env`, then override only generated test-owned project name, loopback ports, and bucket values without printing credentials.
4. Run locked setup, doctor, Compose rendering, `make up`, deterministic seed, the four specification demo targets, `make test`, and `demo-inspect` under explicit per-command and total deadlines.
5. Verify the final inventory includes raw API pages, snapshot Parquet chunks, an archived supplier file, rejected schema-invalid/malformed files, strict manifests, and unchanged checksums after duplicate replay.
6. Run `make down`, then use the exact isolated destructive confirmation only in harness cleanup. Assert no isolated containers, networks, or volumes remain and protected default-project volumes did not change.

The clean export may reuse the local uv cache and already available pinned container images, but the application scenarios access only local Compose services. The report distinguishes setup/image acquisition time from the measured happy-path runtime.

## Non-goals and risks

- No scheduler, UI/dashboard, Prometheus, distributed tracing, orchestration service, data transformation, BI layer, schema evolution, streaming, CDC, or “Possible extensions” work.
- No production fault flags, mutable demo mode in `AppConfig`, manifest additions, aggregate attempt journal, checkpoint object, or alternate recovery implementation.
- The demo harness may use prefix listing for exact read-only inventory. Ingestion services continue to reconcile deterministic exact keys and must not depend on demo reports.
- Abrupt child exit deliberately bypasses Python cleanup. The operating system must release process resources; the parent always opens fresh clients and has bounded cleanup. This does not model power loss inside Garage/PostgreSQL themselves.
- Public demos preserve evidence by design. Users wanting a blank environment must use a separately named isolated project or the existing explicitly confirmed destructive reset; no demo performs implicit deletion.
- Malformed successful HTTP content is terminal under its original deterministic API identity. The lab demonstrates retention and safe re-surfacing, not in-place replacement with corrected bytes.
- PostgreSQL resume requires the emitted descriptor and the original chunk-row setting. Demo artifacts record both, but artifacts are local convenience rather than a durable production checkpoint.
- Clean-export validation can be affected by first-time package or container-image download speed. The three-minute criterion measures the warm local happy path after setup and healthy services, and the final report must state the observed environment and timing boundary.
- Garage has no versioning and conditional create is not an idempotency foundation. All demonstrations remain sequential.

## Documentation basis

Docker Compose service/project isolation and readiness behavior was checked against current Context7 `/docker/compose` documentation: project names scope service operations, a named service can be managed without selecting unrelated project containers, and `up --wait --wait-timeout` provides a bounded running/healthy wait. BI-080 prefers an unreachable loopback S3 endpoint for the outage scenario so the normal local Garage service and developer data are not stopped.

Slice 2 exact inspection was checked against current Context7 `/boto/boto3` documentation: `list_objects_v2` is paginated and accepts server-side `Prefix` filtering, while object bodies returned by `get_object` are streamed and explicitly closed. The implementation independently hashes streamed bytes and deliberately ignores `ETag` as a checksum.

The ingestion and recovery mechanics themselves reuse the version-matched HTTPX, Boto3, Psycopg 3, and PyArrow behavior already documented and acceptance-tested in BI-050, BI-060, and BI-070. No new dependency or ADR is introduced by this plan.
