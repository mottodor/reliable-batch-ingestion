# BI-102 implementation plan — local-preflight test execution

Status: complete; slices 1 and 2 complete

Dependencies: `BI-095` and `BI-101` are complete; [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md) remains binding and is unchanged

Authority: the BI-095 complete local-configuration contract in [`docs/plans/BI-095.md`](BI-095.md), the current implementation in [`scripts/check_local_env.py`](../../scripts/check_local_env.py), the repository test strategy, and the canonical BI-102 scope and acceptance criteria in [`tasks/backlog.yaml`](../../tasks/backlog.yaml)

## Objective

Reduce avoidable process startup in the local-environment preflight tests without weakening the BI-095 configuration, redaction, command-output, or failure-atomicity contract.

The current focused module passes 45 tests in 7.16 seconds on the planning workstation, while the complete 711-test offline suite passes in 9.90 seconds. Most preflight matrix cases start a separate Python interpreter even though `read_env()`, `validate_environment()`, and `main()` are pure, directly callable boundaries. BI-102 moves the validation matrix to those in-process boundaries and retains a minimal real-script smoke boundary.

This task changes tests and task documentation only. It does not change `scripts/check_local_env.py`, `AppConfig`, `.env.example`, Make targets, initialization, runtime behavior, dependencies, accepted ADRs, or operator claims.

## Contracts that must not change

- `AppConfig.from_env()` remains the application-level authority for PostgreSQL, S3, HTTP, file, snapshot, and logging validation.
- `validate_environment()` retains the Compose-only local-port, Garage RPC-secret, and recognized-placeholder checks and delegates application validation exactly as completed by BI-095.
- `check_local_env.main()` retains exit `0` with one `PASS` line for valid input, exit `1` with the `FAIL` heading and redacted bullets for invalid input, and exit `2` for usage errors.
- No test may disclose sentinel credentials, credential-bearing URLs, invalid values designated as secret evidence, generated values, or full dotenv mappings.
- The BI-095 matrix still covers omitted settings from every application group; malformed and non-finite values; invalid enumerations and protocol maxima; file/snapshot cross-field violations; Compose-only ports; placeholders; and Garage RPC-secret syntax.
- `make reset` and `make reset-destructive` remain tested through their real Make/subprocess boundary because those tests verify command delegation rather than pure preflight validation.
- Unit tests remain offline and open no PostgreSQL, HTTP, S3, Garage-admin, or Compose connection.

## Fixed implementation design

### 1. Exercise pure validation in process

Import `read_env`, `validate_environment`, and `main` from `scripts.check_local_env` in `tests/unit/test_local_infrastructure_commands.py`.

Use temporary dotenv files only where parser or path behavior is part of the assertion. For application and local-rule matrices, build the parsed mapping once from the complete initialized test environment, copy it per case, mutate or remove one setting, and call `validate_environment()` directly. Assert fixed variable/constraint names and assert that all sentinel or forbidden values are absent from joined diagnostics.

Do not duplicate `AppConfig` parsing rules in a test helper. BI-102 tests delegation and redaction at the preflight boundary; detailed application rule ownership remains in `tests/unit/test_config.py` and `tests/unit/test_api_config_and_client.py`.

### 2. Preserve one explicit case for every BI-095 category

Retain parameterized cases with useful pytest IDs and independent failure reporting for:

- one omitted PostgreSQL, S3, HTTP, file, snapshot, and logging setting;
- the S3 retry-budget omission retained by the current contract;
- missing, non-integer, zero, and out-of-range Compose-only ports;
- representative invalid application bounds, non-finite values, enumerations, and HTTP/snapshot protocol maxima;
- credential-bearing S3 and mock-API URLs without disclosure;
- file and snapshot spool/maximum cross-field violations;
- all four recognized placeholders;
- malformed Garage RPC-secret text.

The two current tests with identical bodies for invalid application bounds and invalid enumerations/protocol maxima may share one assertion helper or one combined parameter table, provided pytest output still identifies the setting and case clearly.

### 3. Keep a minimal executable-script boundary

Exactly two focused tests may invoke `PREFLIGHT_SCRIPT` as a child process:

1. a complete valid dotenv file proves executable wiring, exit `0`, the exact `PASS` shape, empty stderr, and secret redaction;
2. one invalid dotenv file proves executable wiring, exit `1`, the `FAIL` heading, variable identification, empty stdout, and secret/invalid-value redaction.

No parameterized validation-matrix case may call `_run_preflight()`. Usage exit `2` and additional output variants should call `main()` directly with pytest capture rather than starting another interpreter.

This boundary does not limit the separate Make subprocesses used by destructive-reset contract tests.

### 4. Record deterministic efficiency evidence

Run the focused module before and after the refactor using the same locked environment and record both wall/test durations in the worklog. Timing is evidence, not a flaky pass/fail threshold. The structural acceptance criterion is deterministic: the validation matrix is in process and exactly two focused executable preflight smoke tests start `PREFLIGHT_SCRIPT`.

Confirm collection and behavioral coverage, not a fixed test count. Consolidating identical test bodies may change item count, but every BI-095 category above must remain explicit and independently diagnosable.

## Implementation slices

### Slice 1 — Characterize and move the matrix in process (complete)

1. Record the current focused collection, result, duration, and subprocess structure.
2. Add direct `read_env()`, `validate_environment()`, and `main()` assertions that reproduce the existing success, omission, malformed, boundary, cross-field, placeholder, RPC-secret, redaction, and usage contracts.
3. Keep the existing subprocess cases until the direct matrix proves equivalent, then run the focused config and preflight modules.
4. Use active LSP diagnostics on the changed test path before advancing.

### Slice 2 — Bound executable smoke coverage and close out

1. Remove per-case preflight subprocess execution, leaving exactly the valid and invalid executable-script smoke tests.
2. Retain the unrelated real-Make reset tests unchanged in purpose.
3. Record focused before/after timing and run static, offline, policy, and full repository gates.
4. Update backlog, state, and append-only worklog only after every BI-102 acceptance row passes.

After changing the Python test file, run `lens_diagnostics` with `source=lsp` over that path. An empty session cache is not proof of a clean file.

Integration and clean-export checks are not required because BI-102 changes no product/runtime code, infrastructure, configuration behavior, object contract, or operator command. If implementation crosses that boundary, stop and refine the task before continuing rather than silently expanding validation scope.

## Non-goals and risks

- No change to production validation, dotenv parsing, output wording, exit codes, local-environment initialization, or Make behavior.
- No reduction of BI-095 semantic cases merely to lower pytest item count.
- No broad test-suite helper extraction, integration `conftest.py`, API result factory, large-file split, coverage tool, mutation tool, or new dependency; those audit observations are outside this atomic task.
- No timing assertion in the test suite. Workstation timing varies; deterministic process-count structure is the acceptance boundary.
- No integration-test deletion or replacement of real Garage/PostgreSQL evidence.
- No Possible extensions.
