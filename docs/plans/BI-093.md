# BI-093 implementation plan — terminal output for backend storage failures

Status: done; all five slices are complete

Dependencies: `BI-092` is complete; [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [ADR 0002](../adr/0002-use-whole-file-atomicity-for-file-ingestion.md), and [ADR 0003](../adr/0003-persist-rest-logical-run-manifest.md) remain binding

Authority: [product specification](../specification/batch-ingestion.md), [core contracts](../contracts/core-contracts.md), [storage contract](../contracts/storage-contract.md), the three source-ingestion contracts, and [`BI-090-F03`](../audits/BI-090.md#bi-090-f03)

## Objective

Close `BI-090-F03` so an attempted REST date, file delivery, or PostgreSQL snapshot emits exactly one secret-free source terminal failure event followed by exactly one final `run_summary` when S3 client/session setup or a backend S3 inspection, read, copy, delete, or write fails.

The source service, not the CLI fallback, owns those two terminal records. It must retain the original exception as the chained cause, expose only stable machine codes and fixed messages, preserve all already committed evidence, and keep the existing bounded Botocore retry and source recovery contracts. CLI usage/configuration errors and failures before a logical attempt can have stable trace identifiers remain outside this terminal-summary claim.

BI-093 does not change object keys, manifest schemas, file atomicity, REST aggregate semantics, retry budgets, delivery guarantees, or response-stream deadlines. In particular, it must not absorb BI-094.

## Planning-baseline gap

The audit finding was reproducible from the pre-implementation boundaries:

- `api.service.ingest_api_date()` catches typed domain/storage errors, but `S3Storage` can leak raw `ClientError` or `BotoCoreError`; those bypass `ApiIngestionError`, the terminal `api_ingestion` event, and `run_summary`.
- `files.service.ingest_file_delivery()` has no failure-output boundary. The CLI also stages the landing object before entering that service, so setup and staging failures can produce only a generic `cli_error`.
- `postgres_snapshot.service.ingest_order_snapshot()` emits terminal output only for `SnapshotHandledError`. Its chunk helpers currently convert broad `Exception`, while S3 client setup remains outside the service and fresh-run storage setup occurs before a snapshot descriptor and `batch_id` exist.
- all three CLIs retain generic runtime fallbacks. Those are necessary for non-attempt setup/cleanup defects, but they must no longer be the normal path for backend S3 failures after command validation.
- the existing `s3-unavailable` recovery demo expects API exit `5` and does not require a source terminal event or summary, so it currently proves bounded failure and state preservation but not BI-093 observability.

## Contracts that must not change

- The standard S3 API remains isolated in `src/batch_ingestion/storage.py`; source services continue to depend on narrow storage protocols rather than importing `boto3`.
- Garage versioning, conditional create, concurrent writers, and exactly-once delivery remain outside the contract.
- Raw payload, page, aggregate, file-disposition, snapshot-chunk, and manifest keys and bytes remain unchanged.
- No failed REST aggregate, failed file manifest, or failed snapshot manifest is created for a transient backend failure.
- Existing successful/rejected event fields and every `RunSummary` field keep their current meaning. `bytes_written` counts only a raw payload whose creation was confirmed; an uncertain backend result does not fabricate a write count.
- Botocore retry settings remain the sole S3 request retry mechanism. BI-093 adds no application retry loop.
- CLI exits remain stable by category: attempted ingestion failures use exit `4`; usage, configuration, and genuinely out-of-attempt setup/cleanup failures retain their existing exits. A CLI must not append a second generic error after a service already emitted terminal output.
- Exception text, response bodies, endpoint URLs, credentials, DSNs, local file contents, source rows, and payload values never enter terminal records.

## Fixed implementation design

### 1. Shared backend-error normalization

Add a source-neutral `StorageBackendError` below `StorageError` in `storage.py`. Every public `S3Storage` operation must translate raw Botocore request failures (`BotoCoreError` and `ClientError`) to this type with `raise ... from error`. Missing-key classification remains the existing explicit `ObjectNotFoundError`; conflicts, verification failures, and size-limit failures keep their existing more-specific storage types.

Do not catch arbitrary `Exception` in the shared adapter. Programming errors, invalid local arguments, event-sink failures, and test-fake defects must remain visible rather than being mislabeled as an S3 outage. No backend exception string or response dictionary is copied into the wrapper message or structured output.

Add one context-owned storage-session helper that constructs the configured S3 client, yields `S3Storage`, and closes the client. It translates known S3 construction/request failures while preserving causes. Source terminal success is emitted only after this context exits cleanly; a setup or close failure before terminal success therefore follows the same one-failure-event/one-summary path. Unit tests inject a `nullcontext`-style provider and never access the network.

### 2. One source-owned attempt boundary

Each source service establishes its `source_date`, `batch_id`, and fresh `run_id` before entering the S3 session, maintains counters from confirmed work only, and owns one terminal emitter. The emitter is called once on success/business rejection or once on handled failure; the CLI never reconstructs a source event or summary.

A small source-local terminal guard may enforce the invariant, but no cross-source event supertype is required. Intermediate `api_retry`, `snapshot_started`, and `snapshot_chunk_completed` records are not terminal records and remain allowed.

Handled backend failure exceptions carry their stable code plus the already emitted event and summary (or equivalent typed terminal result), and preserve the original `StorageBackendError` as their cause. CLI code catches the typed source exception and returns exit `4` without emitting another record. Generic CLI runtime output remains only for defects outside the handled attempt contract.

### 3. REST path

`ingest_api_date()` already derives its identity and attempt IDs before aggregate preflight. Move S3 session acquisition inside that attempt boundary and retain the current page/aggregate ordering. Normalize failures from:

- aggregate preflight and final verification;
- page-pair reconciliation and bounded page-manifest/raw reads;
- raw, page-manifest, and aggregate immutable writes;
- uncertain aggregate inspection;
- S3 session setup/close.

All raw backend failures map to existing `ApiErrorCode.STORAGE_ERROR` and its fixed message. Existing conflict, corruption, and ADR 0003 aggregate codes remain distinct. The summary reflects only confirmed pages, retries, records, duplicates, and raw bytes at the point of failure. Backfill continues to call the same single-date primitive and fail fast; the failed date emits exactly one terminal pair and the backfill layer emits no duplicate summary.

HTTP client setup/cleanup and BI-094 response-deadline behavior remain unchanged.

### 4. File path

Move local-file landing staging from the CLI into the file service attempt so its S3 write is covered by the same trace IDs and failure boundary. The CLI still performs bounded local admission first and passes the admitted seekable stream plus descriptor; `resume` passes no staging stream and uses the same service.

Extend the file event contract with a system-failure form without reclassifying it as a business rejection:

- add `failed` to the terminal outcome vocabulary;
- add a stable nullable system `error_code`, initially `storage_failed` and `storage_state_failed`;
- keep `rejection_code` and validation diagnostics only for whole-file business rejection;
- allow `disposition_key` and duplicate classification to be null when failure occurs before those facts exist;
- retain the known landing/raw/manifest keys, source/date, format, `batch_id`, and current `run_id` for every failure.

A new typed `FileIngestionError` carries the failure event and summary. Storage setup, staging, download, inspection, reconciliation, immutable write, copy, delete, and verification failures use that path. Existing accepted/rejected output remains one `file_ingestion` event plus one summary, and ADR 0002 counters remain unchanged. A storage failure never creates a terminal file manifest and never deletes or rewrites retained evidence.

### 5. PostgreSQL snapshot path

Make S3 session acquisition occur inside `ingest_order_snapshot()` only after a valid descriptor is captured or validated and its `batch_id` is derived. For a fresh `run`, the service therefore opens the bounded read-only snapshot, captures the descriptor, emits `snapshot_started`, and then acquires storage before committing chunks. For `resume`, the supplied descriptor is revalidated by the existing reader before storage mutation.

This ordering guarantees stable trace identifiers for S3 setup and operation failures without inventing a provisional snapshot identity. It does not change the PostgreSQL transaction, watermark, explicit-column query, chunk bounds, or replay-from-start contract.

Narrow the chunk helpers from broad `Exception` conversion to explicit `StorageError` conversion now that the shared adapter normalizes Botocore failures. Map backend setup/read/write/copy/delete failures to existing `SnapshotErrorCode.STORAGE_FAILED`, retain conflict/reconciliation distinctions, emit one `snapshot_failed` plus one summary, and raise `SnapshotHandledError` with the original cause preserved. Source/connection failures before descriptor capture continue to have no fabricated batch ID and remain represented by the existing secret-free CLI fallback.

### 6. Output order, redaction, and counters

For every handled backend failure, output order is:

```text
optional non-terminal source events
-> exactly one source terminal failure event
-> exactly one run_summary
-> typed exception returned to the CLI
```

The terminal event and summary use the same `source_date`, `batch_id`, and `run_id`. Duration is monotonic and non-negative. Counters report confirmed progress only:

- API increments raw bytes only after verified raw creation and records/pages only at their existing confirmed points;
- file reports zero validation counters if download/staging fails before validation and counts canonical raw bytes only after verified creation;
- snapshot may report fetched `records_read` before a failed chunk commit, but increments accepted/duplicate/raw-byte counters only after their existing verification points.

Tests use sentinel secrets, endpoint fragments, backend messages, DSNs, row values, and payload values and assert none occur in serialized events or summaries.

## Non-goals and risks

- No BI-094 slow-trickle deadline repair, BI-095 preflight expansion, or BI-096 clean-commit attestation.
- No new retry loop, runtime dependency, manifest, object key, failed-attempt object, mutable status, or cleanup-based recovery.
- No normalization of arbitrary programming exceptions as storage failures. The shared adapter translates known Botocore/backend failures; unexpected defects retain runtime exit behavior.
- Event-sink write failure is not recursively observable through the same sink and remains a runtime failure.
- A backend may commit a write before returning an error. BI-093 reports only confirmed counters, retains uncertain evidence, and relies on existing deterministic-key reconciliation on rerun; it does not claim transactionality.
- Fresh snapshot S3 setup intentionally follows descriptor capture so a valid batch ID exists. A PostgreSQL failure before descriptor capture still cannot emit a valid `RunSummary` and is not an S3 failure.
- Moving file landing staging into the service changes ownership, not ordering: local admission still precedes S3, landing remains the first stored copy, and canonical raw preservation still precedes validation.

## Documentation basis

Planning checked current Context7 documentation for `/boto/botocore`. Botocore distinguishes SDK/network exception classes from `ClientError` for non-2xx service responses; `ClientError` also exposes backend response details that must not be serialized. BI-093 therefore normalizes both categories at the shared storage boundary, preserves the original exception only through chaining, and exposes fixed source-level codes/messages. No new runtime dependency or ADR is required.
