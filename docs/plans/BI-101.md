# BI-101 — Enforce commit-message format

## Goal

Keep every commit after BI-100 in the accepted form:

```text
type(scope): outcome (BI-NNN)
```

The check must run before a normal local commit and again in the repository verification path so `git commit --no-verify` cannot bypass the durable gate.

## Contract

A valid subject must satisfy all of these rules:

- `type` is one of `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `style`, or `test`;
- `scope` is mandatory lowercase kebab-case using ASCII letters and digits;
- the separator is exactly `: `;
- `outcome` is non-empty, starts with a lowercase ASCII letter or digit, contains no line break, and has no leading or trailing whitespace;
- the suffix is exactly one space followed by `(BI-NNN)` with three decimal digits;
- the referenced task ID exists in `tasks/backlog.yaml`;
- the complete subject is at most 100 characters.

Commit bodies remain optional. Merge, revert, fixup, and squash subjects receive no implicit exception because `main` is intentionally linear and every durable commit must identify its atomic backlog task.

## Enforcement boundaries

- `scripts/check_commit_messages.py` is the single standard-library validator used by every entry point.
- `.githooks/commit-msg` validates the message file before a normal local commit.
- `make hooks-install` explicitly configures this clone with `core.hooksPath=.githooks`; setup remains opt-in and does not mutate Git configuration at import or test time.
- `make commit-message-check` validates committed history after BI-100 commit `a049faf1df760b4794970f9ef81feadf5609815b`.
- `scripts/check-repository-policy.sh`, and therefore `make policy` and `./scripts/verify.sh`, run the same range check.
- Earlier historical subjects remain outside the enforcement range and require no rewrite.

## Acceptance

- valid types/scopes/outcomes/task IDs pass; malformed spacing, casing, scope, suffix, task ID, and oversized subjects fail with bounded diagnostics;
- the hook rejects an invalid message file and accepts a valid BI-101 subject;
- history validation checks every commit after the fixed BI-100 boundary and rejects a bypassed invalid commit;
- hook installation is explicit, idempotent, and sets exactly `.githooks`;
- README or linked contributor guidance documents format, allowed values, installation, manual checking, and the `--no-verify` repository-gate boundary;
- the BI-101 commit itself passes the hook and history check;
- repository policy, lint, offline tests, and full verification pass.
