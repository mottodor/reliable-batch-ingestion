# BI-070 implementation plan — bounded PostgreSQL snapshot ingestion

Status: complete; all five slices and the acceptance matrix passed

Dependencies: `BI-030` and `BI-040` are complete

Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [core contracts](../contracts/core-contracts.md), [storage contract](../contracts/storage-contract.md), and [source contracts](../contracts/source-contracts.md)

## Objective

Implement a bounded, restart-safe daily snapshot of `omni_retail.orders` from PostgreSQL into deterministic Parquet chunks in S3-compatible storage. One physical attempt captures or reuses an explicit upper watermark, reads explicit columns through a Psycopg server-side cursor in a read-only `REPEATABLE READ` transaction, serializes at most one configured chunk at a time, and commits each raw chunk before its terminal manifest.

A connection interruption does not advance a mutable client checkpoint. Recovery starts the same bounded logical snapshot from its first row, reuses complete deterministic chunks, repairs payload-only chunks, and continues. The implementation claims a consistent transaction while one connection remains alive, fixed logical bounds across restart, idempotent chunk writes, and visible conflicts. It does not claim a PostgreSQL snapshot can survive a dead connection, exactly-once delivery, or concurrent-writer safety.

## Existing contracts that must not change

- `BatchIdentity`, `batch_id`, the canonical `raw/...` and `manifests/...` layouts, manifest schema version 1, and `RunSummary` remain unchanged. A change to an existing manifest or object-key contract requires an ADR.
- Manifest cardinality remains one manifest for one immutable raw chunk. There is no mutable aggregate snapshot manifest or checkpoint object in BI-070.
- PostgreSQL manifests use `source_type=postgres_snapshot`, `original_file_name=null`, `content_type=application/vnd.apache.parquet`, and terminal status `succeeded` for a verified chunk.
- A complete chunk preserves its original manifest and `run_id`. A later physical attempt does not rewrite it merely to record a replay.
- Snapshot modules use the shared storage boundary. They must not call `boto3` directly, trust `ETag` as SHA-256, overwrite a conflict, or perform Garage administration.
- PostgreSQL remains a source, not an ingestion service database. BI-070 creates no checkpoint, lease, staging, or metadata table in PostgreSQL.
- Imports remain side-effect free: no environment read, PostgreSQL/S3 client construction, transaction, query, or network request occurs at import time.

No new ADR or runtime dependency is planned. The source-specific identity, watermark, Parquet schema, and chunk naming below specialize the existing contracts without changing them.

## Module and ownership plan

Add `src/batch_ingestion/postgres_snapshot/` with narrow responsibilities:

- snapshot contracts: source allow-list, canonical daily window, captured descriptor, logical identity, resume arguments, chunk names, and event/error types;
- reader: explicit SQL, connection construction, transaction characteristics, upper-bound capture/validation, named server-side cursor lifecycle, and bounded `fetchmany()` calls;
- serializer: strict order-row conversion and deterministic one-chunk Parquet serialization to a context-owned seekable spool;
- ingestion service: chunk reconciliation, raw-before-manifest ordering, duplicate handling, metrics, and restart behavior;
- CLI adapter: strict `run`/`resume` commands, explicit PostgreSQL/S3 resource lifecycle, newline-delimited structured output, and stable exit codes.

Keep the fixed source table and column SQL in the PostgreSQL snapshot module. Do not add dynamic schema/table identifiers or general SQL execution abstractions. Reuse `BatchIdentity`, key helpers, `Manifest`, `RunSummary`, `S3Storage`, and `create_s3_client()` unchanged.

Unit tests use fake connections/cursors, deterministic row tuples, local spools, recording storage fakes, and injected clocks. Integration tests use only the local seeded PostgreSQL and Garage services and clean up only test-owned S3 keys and test-owned order rows.

## Fixed design decisions

### Source, daily window, and commands

The sole production snapshot source is `orders`, mapped statically to `omni_retail.orders`. Its seven selected columns, in canonical order, are:

```text
order_id
customer_id
order_status
shipping_status
currency
total_amount
updated_at
```

The command forms will be:

```bash
make ingest-postgres ARGS="run --source orders --date 2026-09-01"
make ingest-postgres ARGS="resume --source orders --date 2026-09-01 --upper-updated-at 2026-09-01T14:11:00.000000Z --upper-order-id 20260901024 --expected-record-count 24"
make ingest-postgres ARGS="resume --source orders --date 2026-09-01 --empty"
```

`source_date` defines a UTC half-open admission window:

```text
window_start          = YYYY-MM-DDT00:00:00.000000Z, inclusive
window_end_exclusive  = next calendar day at 00:00:00.000000Z, exclusive
```

`run` captures the upper watermark and expected record count before writing S3 data. `resume` requires exactly the descriptor emitted by the interrupted run: either all three non-empty fields or `--empty`. It never silently captures a newer upper bound for an existing physical recovery attempt. All timestamps accepted from the CLI must already use the canonical six-fractional-digit UTC `Z` form, and the upper timestamp must lie in the selected daily window.

The CLI emits `snapshot_started` with the complete non-secret resume descriptor before the first chunk is fetched or written. A failure before that event creates no S3 state and can use `run` again. A failure after it uses `resume` with the recorded fields. README recovery commands are added only when the command exists and passes live tests.

### Consistent upper watermark and transaction

For `run`, one explicitly configured connection enters a read-only `REPEATABLE READ` transaction. The first source query fixes the PostgreSQL MVCC snapshot and captures, within the daily window:

- the greatest ordered `(updated_at, order_id)` pair as the inclusive upper watermark;
- the exact selected record count.

The capture query and extraction cursor run in the same transaction. For a non-empty snapshot, extraction applies both the daily window and the inclusive tuple bound:

```sql
WHERE updated_at >= %s
  AND updated_at < %s
  AND (updated_at, order_id) <= (%s, %s)
ORDER BY updated_at, order_id
```

Every query uses `%s` parameter binding. The table and explicit column list are fixed application constants, not user-provided identifiers. `SELECT *`, `fetchall()`, client-side full-result cursors, interpolated values, and offset pagination are forbidden in the snapshot path.

For `resume`, a new read-only `REPEATABLE READ` transaction validates the supplied descriptor before any S3 mutation. It requires the bounded source to have the same record count and the same greatest tuple as the descriptor, then extracts under that tuple bound. A mismatch fails with a stable `source_snapshot_changed` outcome; it never changes the existing batch identity or deletes prior evidence.

An empty capture has `expected_record_count=0` and no upper tuple. It writes one schema-bearing zero-row chunk. `resume --empty` deliberately selects no rows even if later rows appear for that date; a fresh `run` may capture those rows as a new logical snapshot.

The transaction owns one named Psycopg server-side cursor and closes it, then rolls back/ends the read-only transaction and closes the connection on every path. The cursor uses `fetchmany(configured_chunk_rows)` only. Transaction isolation and read-only settings are applied before transaction start; no connection or cursor is held globally.

Rows inserted or updated above the captured tuple are excluded during the original transaction and every resume. BI-070 does not attempt to preserve an MVCC snapshot after its connection dies. Mutating or deleting rows at or below the bound between attempts is unsupported source drift: descriptor count/boundary checks and immutable chunk comparisons fail when observed, but the plan does not claim a durable historical database snapshot under arbitrary compensating concurrent edits.

### Logical identity and deterministic keys

Create `BatchIdentity(source_type=postgres_snapshot)` with `source_name=orders`, the explicit source date, and these sorted logical parameters:

- `snapshot-contract`: literal `omni-retail-orders-parquet-v1`;
- `window-start`: canonical inclusive UTC timestamp;
- `window-end-exclusive`: canonical exclusive UTC timestamp;
- `upper-updated-at`: canonical captured UTC timestamp or literal `none`;
- `upper-order-id`: decimal order ID or literal `none`;
- `expected-record-count`: canonical non-negative decimal integer;
- `chunk-rows`: configured positive decimal integer.

The chunk row bound belongs in identity because changing it changes row grouping, payload bytes, and object names. Operational timeout, elapsed, spool, maximum-byte, and maximum-chunk limits do not select logical data and are not identity inputs. A future source or serialization semantic change must use a new explicit snapshot-contract version instead of reinterpreting an existing batch.

Payload names use one-based four-digit ordinals:

```text
chunk-0001.parquet
chunk-0002.parquet
...
chunk-9999.parquet
```

They flow through the existing helpers unchanged:

```text
raw/postgres_snapshot/orders/source_date=YYYY-MM-DD/batch_id={batch_id}/chunk-0001.parquet
manifests/postgres_snapshot/orders/source_date=YYYY-MM-DD/batch_id={batch_id}/chunk-0001.parquet.manifest.json
```

The expected record count and configured chunk rows determine the exact chunk count before extraction: `max(1, ceil(record_count / chunk_rows))`. The service rejects a descriptor exceeding the configured maximum or four-digit namespace before a cursor or S3 write is opened. It does not list a prefix to infer progress.

### PostgreSQL row and Parquet contract

Every chunk has this exact non-null Arrow schema and field order:

```text
order_id: int64 not null
customer_id: int64 not null
order_status: string not null
shipping_status: string not null
currency: string not null
total_amount: decimal128(12, 2) not null
updated_at: timestamp[us, tz=UTC] not null
```

Rows must preserve database ordering and values. The adapter rejects booleans where integers are required, non-UTC/naive timestamps, decimals outside exact scale/precision, unexpected status/currency values, and nulls as a source contract failure. It does not trim, normalize, round, reorder, or otherwise transform business values.

One successful `fetchmany()` result is the complete in-memory row bound. The serializer builds only that chunk's Arrow arrays/table and writes one Parquet file to a `SpooledTemporaryFile`; it never accumulates rows from another chunk. Fixed writer options are:

- Parquet format version `2.6`;
- data page version `2.0`;
- compression `NONE`;
- dictionary encoding disabled;
- statistics disabled;
- exactly one row group for the chunk, including the zero-row schema-bearing chunk;
- no generated application metadata, source DSN, query text, or extraction timestamp.

After closing the writer, the service enforces the configured maximum serialized chunk bytes, then streams the spool to calculate exact length and SHA-256 and rewinds it for storage. The spool threshold may spill bytes to local disk and must not exceed the maximum serialized chunk size. The spool and Arrow/Parquet writer are closed on success and every failure.

Byte determinism is required for repeated serialization under the committed Python/PyArrow lock. `snapshot-contract` versioning, strict schema, stable row order, fixed chunk size, and fixed writer options make a serialization change explicit. Cross-version Parquet byte stability is not claimed outside the locked toolchain.

### Configuration and bounded work

Extend explicit typed configuration with positive bounds for:

- PostgreSQL connect timeout;
- PostgreSQL statement timeout;
- snapshot total monotonic elapsed budget;
- rows per fetched/serialized chunk;
- maximum chunks, capped at `9,999`;
- maximum serialized bytes per chunk;
- in-memory spool threshold, no greater than maximum chunk bytes.

The expected count is prevalidated against `chunk_rows * max_chunks`. PostgreSQL statement timeout is set transaction-locally through a parameterized `set_config()` call before capture/validation and extraction. The service checks the total monotonic deadline before and after capture, every fetch, serialization, S3 operation, and final count validation. Psycopg performs no hidden application retry; a failed connection is recovered by a new bounded physical CLI attempt.

Existing S3 total attempts and socket timeouts remain the only object-storage request retry budget. Botocore retries are not multiplied by a snapshot-specific loop. PostgreSQL passwords stay redacted from configuration representations and never enter events, manifests, resume arguments, or exception text.

### Per-chunk processing and commit order

For one captured or supplied descriptor, the service performs this order:

1. Validate command/configuration inputs, create a unique physical `run_id`, and open the bounded PostgreSQL connection plus read-only `REPEATABLE READ` transaction.
2. Capture the descriptor for `run`, or validate the supplied descriptor for `resume`. Derive the identity/batch, precompute the exact expected chunk count, and emit `snapshot_started` before any S3 mutation.
3. Open one named server-side cursor over the explicit ordered query. For each `fetchmany(chunk_rows)` result, validate rows and serialize only that chunk to a bounded seekable Parquet spool.
4. Derive exact raw/manifest keys and reconcile them using the actual serialized length and SHA-256.
5. For `absent`, immutably write and verify the raw Parquet bytes. For `payload_only`, reuse the verified payload. For `complete`, require a strict `succeeded` PostgreSQL manifest with matching source, key, content type, length, and checksum and preserve it unchanged.
6. For `absent` or `payload_only`, write one immutable `succeeded` manifest only after raw verification. Use `original_file_name=null`, `attempt=1`, and the current physical `run_id`.
7. Close the chunk spool before fetching the next batch. No later database row is retained by the service.
8. After cursor exhaustion, require the total fetched rows, produced chunks, and final observed watermark to match the descriptor. Only then emit the terminal success event and final `RunSummary`.

`manifest_only`, malformed manifest, wrong linkage/status/source, payload conflict, oversized chunk, source-contract failure, descriptor drift, deadline exhaustion, and connection/storage failure stop the attempt explicitly. System failures do not create a terminal `failed` manifest that could block safe recovery. Already verified complete chunks remain valid evidence.

### Recovery state matrix

| Observed state | Required rerun behavior |
| --- | --- |
| Descriptor emitted, no chunk objects | `resume` revalidates the bound and starts at chunk 1 |
| Earlier chunks complete, next chunk absent | Replay from row 1, preserve complete chunks, then create the first absent chunk |
| Current chunk payload exists without manifest | Verify exact Parquet bytes and add only the missing succeeded manifest |
| Every expected chunk is complete | Replay verifies every chunk, writes nothing canonical, and reports duplicates |
| Manifest exists without payload | Fail explicitly; do not fabricate payload or delete the manifest |
| Existing raw bytes or manifest linkage conflict | Fail; preserve all evidence and overwrite nothing |
| PostgreSQL connection dies after a complete chunk | Emit handled failure with descriptor; `resume` opens a new transaction and replays safely |
| A row is inserted above the captured bound before resume | Descriptor validation/extraction excludes it; the original batch inventory stays unchanged |
| Bounded source count or greatest tuple changed | Fail `source_snapshot_changed` before S3 mutation in that attempt |
| S3 is unavailable after a fetch | Fail within bounded S3 settings; `resume` re-fetches from chunk 1 and reconciles deterministic keys |
| Process stops after raw write and before manifest | `resume` observes `payload_only` and writes only the missing manifest |

No client-side “last fetched row” checkpoint is trusted after failure. Advancing directly to a later key would risk skipping the interrupted fetch and is forbidden. Replay cost is bounded by the captured record count and configured chunk/chunk-count limits.

### Metrics, events, and exit codes

Snapshot metric meanings are:

- `records_read`: source rows returned by completed `fetchmany()` calls in the current physical attempt;
- `records_accepted`: rows represented by successfully reconciled succeeded chunks in the current attempt;
- `records_rejected`: always zero; PostgreSQL source-contract/system failures are not business-row quarantine;
- `pages_fetched`: always zero;
- `bytes_written`: newly created canonical raw Parquet bytes only, excluding manifests and unchanged chunks;
- `retry_count`: always zero; a resume is a new physical attempt and S3 transport retries remain internal to bounded Botocore configuration;
- `duplicate_count`: number of complete pre-existing chunks reused in the current attempt;
- `duration_seconds`: injected monotonic elapsed time for the physical attempt.

Events are newline-delimited compact JSON. `snapshot_started`, per-chunk completion, terminal success, and handled failure include only applicable non-secret fields: source date, batch/run IDs, descriptor values, chunk ordinal/key, status/error code, and counters. They never include the DSN, host/user/password combination, SQL exception text, query values beyond the public descriptor, or row contents.

The PostgreSQL CLI uses the existing exit-code classes:

- `0`: completed new snapshot or complete replay;
- `2`: CLI/descriptor usage error before connections are created;
- `3`: invalid configuration;
- `4`: handled source drift, connection, serialization, reconciliation, conflict, deadline, or storage failure;
- `5`: unexpected runtime setup/cleanup failure.

## Non-goals and risks

- No CDC, incremental cross-batch checkpoint, scheduler, generic table exporter, query language, user-provided SQL, transformed analytical table, schema evolution, multipart upload, or concurrent writer coordination.
- No PostgreSQL checkpoint/service tables, exported snapshot keeper, replication slot, long-lived recovery daemon, aggregate manifest, or mutable attempt journal.
- Recovery replays the fixed bounded query from its first row; it does not seek after the last completed chunk. This is deliberate to prevent a lost or partially fetched chunk from being silently skipped.
- A PostgreSQL MVCC snapshot ends with its connection. Count/boundary validation and immutable chunk checks detect ordinary drift, but arbitrary compensating edits below the bound can evade descriptor checks before an unpersisted chunk. Such concurrent source mutation is outside BI-070's sequential lab contract and must not be described as a durable historical snapshot.
- Holding a read-only transaction while each chunk is written to S3 is acceptable for the bounded local lab but would require a different production-scale design.
- Chunk size is part of logical identity. Operators must use the original descriptor and configured chunk size to resume the same batch; a changed chunk size intentionally creates another batch identity.
- PyArrow may encode its implementation version in Parquet metadata. Exact replay bytes are guaranteed only under the committed lock/toolchain; a future writer/version change requires a new snapshot-contract version.
- No terminal failed manifest is written for connection, deadline, source drift, or storage errors. Structured events and retained complete/payload-only objects provide recovery evidence without poisoning the canonical terminal manifest set.
- Garage lacks versioning, and application-level check-then-write is not safe for concurrent writers. BI-070 remains sequential and does not claim exactly-once delivery.

## Documentation basis

The database plan uses current Context7 Psycopg 3 documentation from `/websites/psycopg_psycopg3`:

- a named cursor created by `Connection.cursor(name=...)` is a server-side cursor and supports `fetchmany()`;
- cursor and transaction context managers release server and transaction resources;
- transaction characteristics such as isolation level and read-only mode must be configured before transaction start and apply to explicit `Connection.transaction()` blocks;
- runtime values are passed as the second `execute()` argument rather than interpolated into SQL.

The Parquet plan uses current Context7 Apache Arrow documentation from `/apache/arrow`:

- `pyarrow.parquet.ParquetWriter`/`write_table()` accepts an explicit schema and bounded table/row-group writes;
- format version, data-page version, compression, dictionary encoding, and statistics are explicit writer controls;
- BI-070 serializes one fetched chunk at a time and never uses a whole-snapshot Arrow table.

S3 behavior reuses the already documented and integration-tested Boto3/Garage shared storage contract. No new library or dependency is introduced by this plan.
