# BI-020 implementation plan — Local Compose infrastructure

Status: planned, not started  
Dependency: `BI-010` is complete  
Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md)

## Objective

Provide a reproducible local PostgreSQL and Garage stack that starts from an explicitly configured `.env`, becomes ready within a bounded time, bootstraps the configured S3 bucket idempotently, preserves both services' data across ordinary `down/up`, and makes data deletion unmistakably explicit.

This task establishes infrastructure only. It does not add the mock API, OmniRetail source schema/data, shared application S3 adapter, or ingestion behavior; those belong to `BI-040`, `BI-030`, and later tasks.

## Fixed decisions

### Images and services

- Use `postgres:17.6-bookworm` for PostgreSQL. The patch-level and distribution-specific tag avoids a floating major or operating-system variant.
- Use the ADR-mandated `dxflrs/garage:v2.4.1` image unchanged.
- Define only long-running `postgres` and `garage` services in this task. Do not pull the future mock API into BI-020.
- Expose PostgreSQL on the configured host port, Garage's S3 API on port 3900, and Garage's admin/health API on port 3903. Garage-internal RPC does not need a host port.

### Configuration and secrets

- Keep `.env.example` as a committed template containing variable names and non-secret placeholders; keep `.env` ignored and required for lifecycle commands.
- Reuse the BI-010 application variables (`POSTGRES_*`, `S3_*`) instead of creating a second credential namespace.
- Map `S3_ACCESS_KEY`, `S3_SECRET_KEY`, and `S3_BUCKET` to Garage's `GARAGE_DEFAULT_ACCESS_KEY`, `GARAGE_DEFAULT_SECRET_KEY`, and `GARAGE_DEFAULT_BUCKET` only inside Compose.
- Add any infrastructure-only values, such as host port overrides, to `.env.example` with explicit safe defaults. Do not place credentials in `compose.yaml`, Garage configuration, command arguments, logs, or documentation.
- Render Compose in verification with `.env.example`; require a real ignored `.env` for commands that start or mutate local services.

### Persistence

- Use named volumes for PostgreSQL data and for both Garage metadata and object data.
- Mount a committed, secret-free Garage configuration that points metadata and data to their separate persistent mount paths.
- `make down` removes containers and the network only. It must not pass `--volumes`.
- Volume removal belongs only to the explicitly confirmed destructive reset path.

### Readiness and bootstrap

- Give PostgreSQL a bounded `pg_isready` healthcheck using the configured database and user.
- Give Garage a bounded healthcheck based on its local status command; additionally verify the documented admin `GET /health` endpoint from the integration harness.
- Implement `make up` with `docker compose up --detach --wait --wait-timeout <bounded-seconds>` so failure is reported instead of hidden by a sleep.
- Start Garage with its v2.4 single-node/default-bucket mechanism. This keeps Garage-specific administration in infrastructure and uses the configured fixed access key, secret key, and bucket.
- Treat repeatability as a tested property, not an assumption: running bootstrap/`make seed` more than once must preserve the same bucket, credentials, and existing sentinel object.
- In BI-020, `make seed` means “idempotently ensure infrastructure bootstrap and readiness.” It does not create OmniRetail rows or generated fixtures; BI-040 will extend its behavior for deterministic source data.

### Lifecycle commands

Add these public Make targets with bounded behavior and accurate help text:

- `make up` — preflight `.env`, start services, wait for health, and ensure bootstrap;
- `make down` — stop the stack without deleting named volumes;
- `make logs` — show/follow service logs;
- `make seed` — rerun the idempotent infrastructure bootstrap/readiness check;
- `make integration` — run infrastructure-marked tests against the local stack;
- `make reset` — print a destructive warning and exit without deleting data;
- `make reset-destructive CONFIRM=destroy-local-data` — require the exact confirmation token, then remove containers and named volumes. A missing or wrong token must fail closed.

The exact destructive target name may change during implementation only if the resulting command remains equally explicit and README examples are updated in the same change.

## Test-first implementation slices

### Slice 1 — Static Compose contract

1. Add failing policy/tests for exact image tags, named volumes, required healthchecks, secret-free committed configuration, and non-destructive normal shutdown.
2. Add `compose.yaml`, the Garage configuration, and `.env.example` wiring needed to satisfy those tests.
3. Make `docker compose --env-file .env.example config --quiet` pass from a clean checkout without creating `.env`.

### Slice 2 — Bounded startup and idempotent bootstrap

1. Add an integration test that checks PostgreSQL connectivity, Garage cluster health, and existence/accessibility of the configured bucket through the standard S3 API.
2. Add the Make/preflight/bootstrap scripts needed for `make up` and `make seed`.
3. Run bootstrap twice and verify that the second execution neither rotates credentials nor replaces/deletes an existing sentinel object.

### Slice 3 — Persistence and destructive reset

1. Add a bounded persistence exercise that writes a PostgreSQL marker and an S3 sentinel, performs ordinary `make down` then `make up`, and verifies both values remain.
2. Add fail-closed tests for `make reset` and for missing/incorrect destructive confirmation.
3. Verify the confirmed destructive reset removes both services' volumes; after a fresh start, the previous markers must be absent and bootstrap must recreate only the configured infrastructure.

### Slice 4 — Operator documentation and closeout

1. Update `README.md` with prerequisites, `.env` setup, lifecycle semantics, health inspection, seed scope, persistence expectations, and the exact destructive warning/command.
2. Keep `docs/STATE.md`, `docs/WORKLOG.md`, and `tasks/backlog.yaml` synchronized when implementation is complete; advance the active task only after every acceptance check passes.
3. Run the required validation matrix and record only commands actually executed.

## Acceptance evidence

BI-020 is complete only when all of the following evidence exists:

| Requirement | Evidence |
| --- | --- |
| Compose is valid and images are pinned | `docker compose --env-file .env.example config --quiet`; static contract test confirms `postgres:17.6-bookworm` and `dxflrs/garage:v2.4.1` |
| Startup is bounded and ready | `make up` succeeds via Compose `--wait` with an explicit timeout; both containers report healthy |
| Bootstrap is idempotent | repeated `make seed` succeeds and an existing S3 sentinel remains byte-identical |
| Ordinary lifecycle preserves state | PostgreSQL and S3 markers survive `make down` followed by `make up` |
| Reset is explicit and destructive only after confirmation | `make reset` and an incorrect confirmation do not delete markers; the confirmed destructive target removes volumes and markers |
| Secrets stay local | `.env` remains ignored; committed files contain placeholders only; credentials come from `.env` at runtime |
| Infrastructure behavior is covered | `make integration` passes against local Compose services with all waits bounded |
| Repository remains healthy | LSP diagnostics for changed Python files, `make lint`, relevant tests, and `./scripts/verify.sh` pass |

## Validation matrix

Run in this order during implementation:

```bash
./scripts/doctor.sh
docker compose --env-file .env.example config --quiet
make lint
make test
cp .env.example .env        # local ignored file; replace placeholders before startup
make up
make seed
make integration
make down
make up                     # persistence verification is part of the integration harness
make reset                  # must warn and preserve data
make reset-destructive CONFIRM=destroy-local-data
./scripts/verify.sh
```

Do not report `make up`, persistence, reset, or integration as passing unless the corresponding command and state assertions were actually executed.
