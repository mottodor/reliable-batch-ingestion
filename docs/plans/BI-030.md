# BI-030 implementation plan — Shared S3 storage boundary

Status: complete; all four slices and acceptance checks passed

Dependency: `BI-020` is complete

Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md)

## Objective

Provide one typed, reusable storage boundary for all ingestion modules. It must construct the configured path-style S3 client, preserve payload bytes under deterministic keys without silently overwriting different content, move objects with `copy -> verify -> delete`, and classify payload/manifest recovery state without mutating it.

The boundary uses only the standard S3 API through `boto3`. Garage administration remains in infrastructure code. API, file, and PostgreSQL source behavior remains in BI-050, BI-060, and BI-070.

## Fixed decisions

### Module and ownership

- Add the shared implementation under `src/batch_ingestion/storage.py`; source-specific modules must use it rather than call `boto3` directly.
- Keep client construction explicit. Importing the package must not read environment variables, resolve credentials, or open a network connection.
- Accept `StorageConfig` and/or an injected typed S3 client so unit tests can exercise behavior without network access.
- Expose typed results for “created versus identical existing object,” “moved versus already moved,” and reconciliation state. Use dedicated exceptions for content conflict and failed verification; do not collapse access, service, or malformed-data failures into “not found.”
- Add no runtime dependency: `boto3`, `botocore`, and S3 type stubs are already present through the locked dependency set.

### Client configuration and retry budget

Extend the storage configuration with explicit positive values for:

- total S3 request attempts, including the initial request;
- connect timeout seconds;
- read timeout seconds.

Add corresponding placeholder-safe values to `.env.example`. Client construction must pass the configured endpoint, region, access key, and secret key directly and use `botocore.config.Config` with:

- Signature Version 4;
- `s3={"addressing_style": "path"}` from the validated application setting;
- standard retry mode;
- `total_max_attempts`, not `max_attempts`, so the value always includes the initial request;
- explicit connect and read timeouts.

Do not add a second application retry loop around Botocore in BI-030. Each storage operation has a fixed number of S3 calls, and each call has explicit attempt and socket-timeout bounds. This avoids multiplicative nested retries. Credential values must not appear in object metadata, exceptions created by the boundary, manifests, or logs.

### Verification rules

- SHA-256 over object bytes is the authority for content identity. Never interpret `ETag` as a SHA-256 digest.
- Stream local and remote bodies in bounded chunks and close every `GetObject` streaming body, including error paths. Do not load a raw object into memory.
- An immutable write accepts a seekable binary stream positioned at its start, an expected byte length, expected lowercase SHA-256, content type, and deterministic key. Reject a non-seekable stream or local length/checksum mismatch before sending a write.
- Store the SHA-256 as S3 user metadata for inspection, but do not trust metadata alone: successful and pre-existing objects are verified by streaming their bytes. Compare content length as an additional invariant.
- Treat only S3 missing-object responses (`404`, `NoSuchKey`, or `NotFound`) as absence. Propagate authorization, endpoint, throttling, malformed response, and other failures.
- Keep manifest reads bounded: inspect `ContentLength` first, reject a manifest above a documented small maximum, then parse it through the existing strict `Manifest.from_json` contract.

### Immutable write state machine

For one deterministic key under the documented single-writer assumption:

1. Validate the local stream's length and SHA-256, then rewind it.
2. Probe the destination.
3. If it exists, stream and hash it. Return the idempotent “unchanged” result only when length and bytes match; otherwise raise a conflict without calling `PutObject`.
4. If it is absent, call `PutObject` with the content type and checksum metadata.
5. Read the stored object and verify its length and SHA-256 before reporting success.
6. If the write outcome is uncertain, propagate the failure. A retry of the whole primitive safely re-enters at step 2 and classifies the actual state.

Garage has no bucket versioning, and conditional `PutObject` is not a contract foundation. The check-then-put interval is therefore not safe for concurrent writers. BI-030 must document and test sequential idempotency, but must not claim concurrency safety or exactly-once delivery.

### Copy-verify-delete movement

The move primitive requires distinct source and destination keys plus the expected source length and SHA-256. It follows this recoverable state machine:

1. Inspect and byte-verify the source when present.
2. Inspect the destination. Different content is a conflict and leaves the source untouched. Identical content means the copy phase already completed.
3. If the destination is absent, call S3 `CopyObject` with the source bucket/key and metadata-copy semantics.
4. Stream and verify the destination bytes, content length, content type, and user metadata against the source. Do not use `ETag` for this check.
5. Delete the source only after destination verification succeeds.
6. Confirm that the source is absent and the verified destination remains present before reporting completion.

A failure before copy leaves source only. A failure after copy and before confirmed delete may leave both identical objects. A successful delete leaves destination only. Re-entry must converge from all three states: source-only repeats copy, both-identical skips copy and retries delete, and destination-only returns “already moved” after verifying the caller's expected checksum and length. Source missing plus destination missing, or any destination mismatch, is an explicit failure. The initial implementation uses single-call `CopyObject`; multipart movement is outside the core scope.

### Payload-without-manifest reconciliation

Implement a read-only primitive over one deterministic payload key and its derived manifest key. It must return a typed state and evidence, never delete or repair objects itself:

- `absent` — neither object exists;
- `payload_only` — the payload exists and its streamed bytes match the caller's expected length/checksum, but the manifest is absent;
- `complete` — both exist; the manifest parses strictly, points to the payload key, and its length/checksum agree with the streamed payload;
- `manifest_only` — invalid recovery state requiring explicit handling;
- conflict/corruption — malformed manifest, wrong linkage, or any length/checksum mismatch; report through a dedicated exception rather than an apparently healthy state.

This split keeps recovery policy in the future ingestion adapters. For `payload_only`, a new physical attempt may reuse the verified immutable payload and write the missing manifest. For `complete`, a repeated run reuses the existing successful pair instead of rewriting a manifest containing a different `run_id`. Reconciliation uses exact deterministic keys and does not rely on eventually consistent prefix listing.

### Slice 2 — Copy-verify-delete movement

1. Add failing unit tests for source-only, both-identical, destination-only, destination-conflict, copy failure, verification failure, delete failure, and post-delete verification failure.
2. Implement movement using `CopyObject`, streamed verification, then `DeleteObject`; preserve source metadata and content type.
3. Add Garage integration coverage for the happy path, metadata preservation, and recovery from a pre-created both-identical state. Clean dedicated test-prefix objects in `finally`.

### Slice 3 — Payload/manifest reconciliation and endpoint failure

1. Add failing unit tests for `absent`, `payload_only`, `complete`, `manifest_only`, malformed/oversized manifest, wrong manifest key linkage, and payload checksum/length conflict.
2. Implement read-only reconciliation using `manifest_key_for()` and `Manifest.from_json()`; do not add source-adapter policy.
3. Add Garage integration coverage for payload-only detection followed by missing-manifest creation through immutable write, then complete-state detection.
4. Exercise bounded unavailable/transient-endpoint behavior with a deterministic local fault endpoint and a test deadline. Assert the configured total attempt budget; do not use arbitrary sleeps or the public network.

1. Add `docs/storage-contract.md` describing public outcomes, failure states, retry bounds, checksum authority, move recovery, reconciliation, and the single-writer limitation.
2. Update README only with commands and behavior that exist by this point.
3. Run the complete acceptance matrix against Garage.
4. Mark BI-030 done and advance the active task only after all evidence passes; synchronize `tasks/backlog.yaml`, `docs/STATE.md`, and append `docs/WORKLOG.md`.

## Non-goals and risks

- No source-specific ingestion, CLI, backfill, file validation, or snapshot behavior.
- No Garage administration in application code.
- No multipart upload/copy, bucket versioning, distributed lock, or concurrent-writer guarantee.
- No overwrite-based repair. A conflicting deterministic key is surfaced for operator or higher-level recovery policy.
- Botocore retries individual requests. A multi-call primitive can fail between calls; deterministic re-entry and explicit state verification provide recovery.

## Documentation basis

The plan uses current Context7 documentation from `/boto/boto3`:

- client-specific `botocore.config.Config`, SigV4, and S3 addressing-style configuration;
- standard retry mode and `total_max_attempts`, whose value includes the initial request;
- S3 `PutObject`, `HeadObject`, `GetObject`, `CopyObject`, and `DeleteObject` behavior and metadata handling.

ADR 0001 remains authoritative where Garage differs from AWS S3: conditional create and versioning are not used as correctness foundations, and `ETag` is never treated as SHA-256.
