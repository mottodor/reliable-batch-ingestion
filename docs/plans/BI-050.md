# BI-050 implementation plan — REST API ingestion and backfill

Status: complete; all five slices and the full acceptance matrix passed on 2026-10-14

Dependencies: `BI-030` and `BI-040` are complete

Architecture authority: [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [core contracts](../core-contracts.md), and [storage contract](../storage-contract.md)

## Objective

Implement bounded, restart-safe ingestion for the two deterministic REST resources created by BI-040. One single-date primitive must fetch strictly validated pages, preserve every HTTP 200 page body before parsing it, write one immutable manifest per raw page, resume from deterministic payload/manifest states, and emit a final structured summary. Inclusive date-range backfill must call that same primitive rather than introduce a second ingestion path.

The implementation claims deterministic keys, idempotent immutable writes, and safe sequential redelivery. It does not claim exactly-once delivery or concurrent-writer safety.

## Existing contracts that must not change

- `BatchIdentity`, `batch_id`, raw object keys, manifest keys, manifest schema version 1, and `RunSummary` remain unchanged. Changing any of them requires an ADR.
- Manifest cardinality remains one manifest per raw page. The “logical-run manifest” requirement is satisfied by the complete page-manifest set sharing one `batch_id`, plus the final `RunSummary`; BI-050 must not add a second mutable aggregate manifest.
- Raw keys use `page-0001.json`, `page-0002.json`, and so on under the existing API key prefix. Page numbers identify payloads inside one batch and are not separate batch identities.
- API manifests always set `original_file_name` to null. A valid page receives terminal status `succeeded`; a preserved HTTP 200 body that cannot be decoded or validated receives terminal status `failed`.
- The shared `S3Storage` boundary owns all S3 access. API modules must not call `boto3` directly, use `ETag` as SHA-256, overwrite conflicts, list prefixes to infer correctness, or perform Garage administration.
- A new `run_id` is created for every command attempt. A pre-existing complete page retains the original manifest and its `run_id`; it is never rewritten merely to record a new attempt.
- Imports remain side-effect free: no environment read, HTTP client, S3 client, sleep, or clock access occurs at import time.

No ADR or new runtime dependency is required for this plan because it uses the existing `httpx`, identifier, manifest, summary, and storage contracts without changing their schemas or delivery claims.

## Module and ownership plan

Add a `src/batch_ingestion/api/` package with narrow responsibilities:

- source descriptors: the allow-listed `fx-rates` and `shipping-statuses` names, their `/v1/...` paths, and source-specific page validators;
- retry policy: pure response/exception classification, `Retry-After` parsing, and bounded delay calculation;
- HTTP page fetcher: one injected `httpx.Client`, response-size enforcement, byte spooling, checksum calculation, and retry execution;
- ingestion service: identity/key derivation, S3 reconciliation, raw-before-parse ordering, page-manifest creation, pagination invariants, metrics, and single-date/backfill orchestration.

Add `src/batch_ingestion/cli.py` only when the service contract is tested. The CLI owns argument parsing, explicit configuration/client construction, structured output, and exit codes; it contains no retry, pagination, storage, or backfill business rules.

Unit tests use injected transports, storage fakes, clocks, monotonic time, and sleep functions. Integration tests use only the local Compose mock API and Garage. Production CLI options do not accept arbitrary URLs, headers, or query parameters.

## Fixed design decisions

### Source selection and logical identity

The production source allow-list is:

| CLI source | Request path | Canonical `source_name` |
| --- | --- | --- |
| `fx-rates` | `/v1/fx-rates` | `fx-rates` |
| `shipping-statuses` | `/v1/shipping-statuses` | `shipping-statuses` |

For one date, create `BatchIdentity(source_type=api)` with these sorted logical parameters:

- `resource-path`: the versioned resource path;
- `page-size`: the configured positive page size.

The base URL is deployment configuration, not logical source identity. Page number is represented by the payload name, not the batch identity. Mock fault controls (`scenario`, `scenario_key`, and `fault_page`) alter delivery behavior rather than selected business data and are excluded from identity. Integration tests supply only those three known controls through an injected request-parameter provider; BI-050 does not expose arbitrary query injection in the production CLI.

Changing source bytes for the same source/date/path/page-size is a deterministic-key conflict, not an overwrite. This intentionally exposes upstream mutation or an omitted identity parameter.

### Configuration and hard bounds

Retain the existing explicit values for base URL, connect timeout, read timeout, total HTTP attempts, and backoff base. Add positive, validated settings for:

- maximum exponential-backoff delay;
- maximum total retry elapsed time for one page;
- page size, capped at the mock contract maximum of 100;
- maximum pages per logical batch, capped at 9,999 to match four-digit payload names;
- maximum response-body bytes per page;
- maximum inclusive backfill days.

`httpx.Timeout` is constructed explicitly: connect uses the configured connect timeout, read and write use the configured read timeout, and pool acquisition uses the connect timeout. The client uses `trust_env=False`, the configured base URL, and one context-managed connection pool. Do not enable `HTTPTransport` retries; the application loop is the sole HTTP retry owner, preventing hidden or multiplicative attempts.

Establish one monotonic deadline per page. Before each request, clip every phase timeout to the remaining deadline; check the deadline again before sleeping and after every streamed body chunk. This keeps slow multi-chunk responses inside the same elapsed budget rather than treating HTTPX's per-operation read timeout as a total-response deadline.

Require a `Content-Type` whose base media type is `application/json`, retain its trimmed full value for raw-object metadata and the manifest, and reject a missing or incompatible value as a protocol failure. Read response bodies in bounded chunks into a seekable spooled temporary file while computing SHA-256 and length. Stop with a typed size-limit failure as soon as the configured maximum would be exceeded. A page is individually bounded and may be loaded for JSON parsing only after its raw bytes are successfully preserved; the complete multi-page run is never accumulated in memory.

### Retry and error classification

Each page starts at attempt 1. `HTTP_MAX_ATTEMPTS` includes the initial request. The loop is also bounded by monotonic elapsed time; no sleep may begin if its full delay would exceed the remaining page retry budget.

Classify outcomes explicitly:

| Outcome | Retry behavior |
| --- | --- |
| HTTP 200 | Do not retry; preserve bytes before decode/validation |
| HTTP 429 | Retry within both budgets; honor a valid `Retry-After` |
| Other HTTP 4xx | Permanent; return after one request |
| HTTP 5xx | Retry with bounded exponential backoff |
| Connect/read/write/pool timeout or transport failure | Retry with bounded exponential backoff |
| Redirect, unexpected non-200 2xx, or other status | Permanent protocol failure |
| JSON, schema, or pagination validation failure after HTTP 200 | Do not retry that response; preserve it and record failure |
| S3/configuration/programming failure | Never enter the HTTP retry loop; fail the command |

Parse `Retry-After` as either non-negative decimal seconds or an HTTP date using an injected UTC clock. A past date means zero delay. A syntactically invalid value falls back to exponential backoff. A valid delay is used exactly when it fits the remaining elapsed budget; otherwise fail as retry-budget exhausted rather than truncating the server-requested delay.

Fallback delay is deterministic and has no jitter:

```text
min(HTTP_BACKOFF_BASE_SECONDS * 2 ** (attempt - 1), HTTP_BACKOFF_MAX_SECONDS)
```

Inject `sleep`, monotonic time, and wall-clock time so unit tests assert delays and deadlines without real sleeping. `retry_count` increments only when another request is actually attempted. Structured retry/error events include the non-secret `source_date`, `batch_id`, `run_id`, page, attempt, classification, HTTP status when present, and selected delay; never log request/response headers, response bodies, credentials, or full query strings.

HTTP error bodies are not business pages and are not written under `page-NNNN.json`; otherwise a transient 429 or 5xx would conflict with the later successful page. Their status/classification is traceable through structured error output. Every HTTP 200 body, including malformed JSON, is a candidate raw page and must be preserved before parsing.

### Page envelope and pagination invariants

After preservation, decode UTF-8 JSON and require an object with exactly the documented envelope fields:

```text
source, source_date, page, page_size, total_pages,
total_records, next_page, items
```

Validate types strictly, reject booleans where integers are required, and validate source-specific item fields against `docs/source-contracts.md` without transforming or reserializing the raw body. Require:

- response source/date/page/page-size equal the request identity;
- positive `total_pages` within the configured maximum;
- non-negative `total_records`;
- page 1 establishes `total_pages` and `total_records`, which later pages must repeat;
- `next_page` is exactly `page + 1` before the last page and null on the last page;
- item counts are consistent with page size and total records, including the final page;
- traversal is strictly increasing and cannot cycle, skip, or fetch beyond the established last page.

A schema or pagination violation follows the same preserved-then-failed path as malformed JSON.

### Raw-page and manifest state machine

For each HTTP 200 response:

1. Stream the complete bounded body to a seekable temporary stream and compute its length/SHA-256.
2. Derive `page-NNNN.json` and the existing manifest key.
3. Call `reconcile_payload_manifest()` with the fetched length/checksum.
4. Handle the observed state:
   - `absent`: immutably write and byte-verify the raw payload;
   - `payload_only`: reuse the already verified payload without another `PutObject`;
   - `complete`: require an API manifest with matching identity and a supported terminal status; never replace it;
   - `manifest_only`: fail explicitly without deleting or fabricating data;
   - conflict/corruption: propagate the storage error and leave objects unchanged.
5. Only after the payload is verified in S3, decode and validate the fetched bytes.
6. For `absent` or `payload_only`, create one canonical manifest:
   - `succeeded` for a valid page;
   - `failed` for malformed UTF-8/JSON, item schema, or pagination content;
   - `attempt` is the 1-based HTTP request attempt that produced this body;
   - `extracted_at` comes from an injected timezone-aware UTC clock after body receipt.
7. Write the manifest immutably through `S3Storage.write_immutable()` with JSON content type.
8. For `complete`, compare the recorded terminal status with the current deterministic result. Reuse `succeeded`; re-surface a recorded `failed` page as failure. Any impossible status/result mismatch is an explicit conflict rather than a repair.

A process failure after payload upload but before manifest upload leaves `payload_only`. Rerunning fetches the deterministic page, verifies the existing bytes, and writes only the missing manifest with the new run's `run_id`. A complete successful pair is counted as a duplicate/reused page and produces no writes. Recovery uses exact keys, not prefix listing.

The application runs under the existing sequential single-writer assumption. Two processes ingesting the same batch concurrently remain unsafe.

### Metrics and final outcomes

Create one `run_id` per single-date invocation. Emit exactly one final `RunSummary` on both success and handled failure, plus a separate structured success/failure event because schema version 1 intentionally has no run-status or error-reason field.

Metric definitions for BI-050 are:

- `records_read`: item records in successfully validated pages;
- `records_accepted`: equal to `records_read` because BI-050 performs no transformation/rejection split;
- `records_rejected`: zero for valid pages; malformed pages have no trustworthy record count;
- `pages_fetched`: complete HTTP 200 bodies received, including a malformed body;
- `bytes_written`: newly created raw payload bytes only, excluding manifest metadata and unchanged objects;
- `retry_count`: additional HTTP requests actually made after first attempts;
- `duplicate_count`: complete successful page pairs reused without mutation;
- `duration_seconds`: injected monotonic elapsed time for the single-date run.

A failed command exits non-zero after emitting the failure event and summary. Permanent 4xx, exhausted 5xx/transport retries, invalid body, pagination violation, manifest-only state, and storage conflict use distinct typed error codes. Exceptions are not swallowed or rendered with secrets.

### Inclusive backfill and CLI

Expose these implemented command forms through `make ingest-api ARGS="..."`:

```bash
make ingest-api ARGS="run --source fx-rates --date 2026-09-01"
make ingest-api ARGS="backfill --source fx-rates --from 2026-09-01 --to 2026-09-07"
```

Use strict canonical ISO dates. Reject `from > to` and a range exceeding the configured maximum before opening HTTP or S3 clients. Iterate dates sequentially and inclusively in ascending order, calling the same single-date primitive with the same source descriptor and page size.

Backfill is fail-fast: stop at the first failed date, return non-zero, and report that date. A rerun of the full requested range safely reuses earlier complete page pairs and continues through the failed date. Do not add a separate backfill storage format, key layout, retry policy, or implementation.

The CLI constructs configuration and clients explicitly, closes them with context managers, emits structured JSON, and maps validation/failure classes to stable non-zero exit codes. It does not expose mock fault controls; integration tests inject those below the CLI boundary.

## Non-goals and risks

- No file ingestion, PostgreSQL snapshot extraction, scheduler, async client, authentication scheme, general-purpose arbitrary REST connector, or concurrent ingestion.
- No aggregate run manifest, manifest reason field, object-key change, or overwrite-based repair. Any such contract change requires an ADR.
- No persistence of transient 429/5xx bodies under business page keys. They are delivery failures, not successful source pages; status and classification remain in structured output.
- A source that changes bytes for the same logical identity produces an intentional immutable conflict. Operators must correct the identity contract or source behavior rather than overwrite raw history.
- `Retry-After` HTTP-date interpretation depends on an injected UTC clock; production wall-clock skew can affect the computed delay, while the total monotonic budget still bounds execution.
- A complete failed manifest is terminal under schema version 1. Retrying unchanged malformed bytes re-surfaces the failure; repaired upstream bytes at the same identity conflict instead of silently replacing evidence.
- Backfill is sequential and fail-fast. Parallelism and continue-on-error aggregation are outside BI-050 and would require an explicit later decision.

## Documentation basis

The plan uses current Context7 documentation from `/encode/httpx/0.28.1`:

- `httpx.Client` provides connection pooling and explicit lifecycle management;
- `httpx.Timeout` supports separate connect, read, write, and pool bounds and raises phase-specific timeout exceptions;
- response status is inspected explicitly, headers are available through `response.headers`, and `iter_raw()` streams response bytes without content decoding;
- `raise_for_status()` would collapse status handling into `HTTPStatusError`, so BI-050 classifies status codes directly before deciding whether to retry or preserve an HTTP 200 body;
- `HTTPTransport(retries=...)` retries connection failures, but BI-050 deliberately leaves transport retries disabled so one application-owned attempt/elapsed budget governs all HTTP retries.
