# BI-040 implementation plan — Deterministic source generators and fixtures

Status: complete; slices 1–5 are complete

Dependency: `BI-020` is complete

Related future consumers: `BI-050`, `BI-060`, and `BI-070`

## Objective

Provide small, reproducible OmniRetail source datasets for every later ingestion path: a PostgreSQL orders table with stable watermarks, paginated REST resources with selectable deterministic faults, and committed supplier-price files in CSV, JSON, and Parquet. A caller must be able to select one seed, reproduce the same logical records, and verify the exact fixture bytes where the locked writer permits that guarantee.

BI-040 creates sources and test data only. It does not persist source payloads to S3, implement ingestion retries, validate delivered files as an ingestion operation, extract snapshots, create manifests, or define backfill behavior.

## Fixed decisions

### Seed and determinism contract

- Use one public non-secret integer `SOURCE_SEED` across PostgreSQL seeding, mock API data, and supplier fixtures. The committed/default seed is `20260901`.
- Validate the seed before changing files or database state. Reject missing, non-decimal, negative, or out-of-range values; never silently choose a random seed.
- Derive every generated value from a canonical tuple containing the seed, source name, source date, and stable row ordinal. Use explicit arithmetic or SHA-256-based selection rather than process-global `random`, Python's salted `hash()`, current time, locale, unordered container iteration, or generated UUIDs.
- Use fixed UTC source dates and timestamps. The default corpus begins on `2026-09-01`; generators must not consult the wall clock.
- Emit records in an explicit stable sort order. A different seed must change at least one business value while preserving each published schema.
- Scope exact Parquet byte reproducibility to the committed `uv.lock`, Python 3.12, and the supported local toolchain. PyArrow writes its implementation version into `created_by`; across another PyArrow version only schema and logical-row equality are promised.

### Ownership and repository layout

- Keep PostgreSQL DDL and data SQL under `postgres/init/` as ordered, versioned files. Run them explicitly from `make seed`; do not rely on `/docker-entrypoint-initdb.d`, because an existing named volume would skip one-time initialization.
- Keep the HTTP source and fault injector under `mock_api/`. It may contain deterministic source generation and local fault-control state, but no ingestion, S3, manifest, retry-client, or backfill logic.
- Keep supplier fixture generation in a typed generator invoked by `scripts/generate_fixtures.py`. Store the small canonical corpus under `fixtures/`; generated code or cache files do not belong there.
- Add `docs/source-contracts.md` during implementation for schemas, seed rules, routes, scenarios, fixture layout, and regeneration commands. README must describe only commands that have been implemented and exercised.
- Add no Python runtime dependency. Use the standard-library HTTP server for the mock source, existing `httpx` for integration probes, existing Psycopg for database assertions, and existing PyArrow for Parquet generation and inspection.

### PostgreSQL source contract

Create the dedicated `omni_retail` schema and an `orders` table with these explicit columns:

- `order_id bigint` primary key;
- `customer_id bigint` not null;
- `order_status text` not null with a documented finite-value check;
- `shipping_status text` not null with a documented finite-value check;
- `currency char(3)` not null with a documented finite-value check;
- `total_amount numeric(12,2)` not null and non-negative;
- `updated_at timestamptz` not null and unique.

Add an index ordered by `(updated_at, order_id)` for the later bounded snapshot query. Generate a small fixed row count across multiple UTC intervals. `updated_at` values must be unique, monotonically ordered by the stable ordinal, and independent of execution time so BI-070 can test lower and consistent upper bounds without a composite-watermark extension.

The schema script must be safely repeatable and the seed script must run in one transaction with `ON_ERROR_STOP`. Seed replacement may truncate and repopulate only `omni_retail.orders`; it must not touch the BI-020 infrastructure probe, Garage, or unrelated PostgreSQL objects. Running the same seed twice must produce the same ordered explicit-column row digest and row count. The selected seed is supplied to `psql` as a quoted variable, not interpolated into shell SQL.

Extend `make seed SOURCE_SEED=<integer>` so it first preserves the existing idempotent infrastructure bootstrap and then applies the versioned schema and deterministic order seed. A failed validation or SQL statement must return non-zero instead of reporting partially seeded success.

### Mock REST API contract

Run the mock source as a third Compose service built from a repository Dockerfile based on the verified patch-level image `python:3.12.12-slim-bookworm`. The service:

- listens on container port `8080` and the configured host `MOCK_API_PORT`;
- receives `SOURCE_SEED` as a non-secret environment value;
- has a bounded healthcheck against `/health` that does not consume or reset fault state;
- starts with no network, PostgreSQL, or S3 access and no import-time connection;
- is covered by the existing bounded `docker compose up --wait --wait-timeout` flow.

Expose these versioned resources:

- `GET /v1/fx-rates`;
- `GET /v1/shipping-statuses`.

Both require an ISO `source_date` and positive `page` and `page_size` values within a documented maximum. Successful responses use UTF-8 canonical JSON and include `source`, `source_date`, `page`, `page_size`, `total_pages`, `total_records`, `next_page`, and a stably ordered `items` array. Invalid route/query input returns a deterministic permanent 4xx response. No endpoint requires or reflects credentials.

Select faults explicitly with query parameters. Use these stable scenario names and semantics:

- `happy` — every valid page succeeds;
- `rate_limit_once` — the first matching request for a caller-supplied scenario key returns `429` with `Retry-After: 1`, then the same page succeeds;
- `permanent_500` — every matching request returns the same `500` response;
- `malformed_json` — the selected page returns status `200`, JSON content type, and deterministic malformed bytes;
- `partial_pages` — at least one earlier page succeeds and the selected later page fails consistently, creating a reproducible partial-run boundary.

State for `rate_limit_once` is isolated by a validated scenario key and protected for the threaded local server. Provide a test-only/local control operation that resets one key or all fault counters deterministically; it must never alter generated source records. Bound retained keys so arbitrary requests cannot grow memory without limit. Health requests and malformed/permanent scenarios must not advance the transient counter.

Unit tests exercise request parsing and response generation without binding a socket. Integration tests use the configured base URL, explicit `httpx` timeouts, unique/reset scenario keys, and no sleeps or public network.

### Supplier fixture contract

Use one schema version and one column order for all valid supplier-price files:

1. `supplier_id` — non-empty string;
2. `product_id` — non-empty string;
3. `price_minor_units` — positive 64-bit integer;
4. `currency` — supported three-letter code;
5. `effective_date` — ISO date in CSV/JSON and `date32` in Parquet.

Use integer minor units so CSV, JSON, and Parquet represent the monetary value without floating-point ambiguity. Canonical valid rows are sorted by `(supplier_id, product_id, effective_date)`.

Generate and commit this minimum corpus:

- valid CSV, JSON, and Parquet files containing the same logical rows;
- empty CSV, JSON, and Parquet files that retain their format/schema where possible;
- schema-invalid CSV, JSON, and Parquet files, such as a missing required field/column or incompatible type;
- a mixed-row fixture containing both valid and business-invalid records without pre-deciding BI-060 whole-file atomicity;
- two delivery directories containing byte-identical files with the same basename;
- two byte-identical files with different basenames for the renamed-content case.

Do not encode BI-060's acceptance/rejection result in the corpus. Scenario metadata identifies the intended condition only; BI-060 will define file atomicity in its own ADR.

For stable bytes:

- CSV uses UTF-8, LF line endings, a fixed header order, deterministic quoting, and a final newline;
- JSON uses UTF-8, fixed key order, fixed separators/indentation, and a final newline;
- Parquet uses an explicit Arrow schema and explicit `write_table` options: Parquet version, row-group size, no compression, no dictionary encoding, statistics setting, and data-page version. No generated timestamp or absolute path may enter metadata.

Write a sorted `fixtures/checksums.json` containing the fixture schema version, seed, relative path, byte length, SHA-256, format, and scenario. This is fixture-generation evidence, not an ingestion manifest and must not be passed to the manifest contract.

Generation accepts an explicit output directory so tests can regenerate into a temporary location. The normal target updates the committed corpus; a separate check target regenerates to temporary storage and compares path set, bytes, checksums, parsed schemas, and logical rows without modifying tracked fixtures.

## Acceptance evidence

| Requirement | Evidence |
| --- | --- |
| One explicit deterministic seed | Unit tests validate `SOURCE_SEED=20260901`, repeat pure generation, reject invalid seeds, and prove another seed changes data without changing schemas |
| Repeatable PostgreSQL source | Same-seed integration runs produce equal count/digest/timestamp bounds; timestamps are UTC and unique; BI-020 marker data remains unchanged |
| Paginated deterministic API | Unit and live HTTP tests traverse both resources and compare canonical page bodies for the same seed |
| Selectable API faults | Live tests observe isolated `429 -> success`, repeated `500`, exact malformed JSON bytes, and one or more successful pages before the configured partial boundary |
| Complete file corpus | Tests parse valid/empty/invalid/mixed CSV, JSON, and Parquet and assert the required path/scenario matrix |
| Byte stability | Two temporary generations and the committed default corpus have identical paths, lengths, SHA-256 values, and bytes under the locked toolchain |
| Duplicate cases | Tests prove same-name duplicate deliveries and same-content/different-name delivery using byte-level SHA-256, without assigning BI-060 outcomes |
| Bounded local operation | Compose startup/health is bounded; HTTP calls have explicit timeouts; fault state is bounded; no public network is used by tests |
| Repository health | LSP diagnostics for changed Python files, `make lint`, `make test`, source integration tests, full `make integration`, and `./scripts/verify.sh` pass |

## Validation matrix

Run incrementally and report only commands actually executed:

```bash
./scripts/doctor.sh
docker compose --env-file .env.example config --quiet
make lint
make test
make fixtures-check SOURCE_SEED=20260901
make up
make seed SOURCE_SEED=20260901
```

The implementation must also exercise every documented fault with bounded live HTTP requests. Integration cleanup may reset mock fault counters and restore the default source seed, but it must not delete unrelated PostgreSQL or S3 data.

## Non-goals and risks

- No REST ingestion, retry loop, S3 payload write, manifest creation, file-ingestion decision, snapshot extraction, backfill, or recovery workflow.
- No file atomicity decision; mixed-row fixtures exist specifically for BI-060 to decide under an ADR.
- No production authentication or public exposure for the local mock source.
- No claim that Parquet bytes remain stable after changing PyArrow, the lockfile, architecture, or explicit writer options. Logical schema/row checks remain required in addition to checksums.
- Stateful `rate_limit_once` behavior can become order-dependent if callers reuse a scenario key without reset. Tests and documentation must always isolate or reset the key.
- Reseeding replaces only the controlled demo orders table. Documentation must make that mutation explicit even though infrastructure volumes and unrelated objects are preserved.

## Documentation basis

The plan uses current Context7 documentation:

- `/websites/postgresql_17` for quoted `psql` variable interpolation and version-matched PostgreSQL 17 SQL behavior;
- `/docker/compose` for a repository-built service, health-based startup, and bounded `up --wait --wait-timeout` behavior;
- `/python/cpython` for `ThreadingHTTPServer`, `BaseHTTPRequestHandler`, and bounded server lifecycle behavior;
- `/apache/arrow` for `pyarrow.parquet.write_table` controls including Parquet version, row-group size, compression, dictionary encoding, statistics, and data-page version. PyArrow's automatic `created_by` metadata is why cross-version byte identity is not promised.
