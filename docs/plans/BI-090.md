# BI-090 execution plan — independent post-completion acceptance audit

Status: complete; all four audit slices closed with findings and bounded maintenance follow-up

Dependency: `BI-080` is complete

Authority: [product specification](../specification/batch-ingestion.md), [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [ADR 0002](../adr/0002-use-whole-file-atomicity-for-file-ingestion.md), and the acceptance criteria in [`tasks/backlog.yaml`](../../tasks/backlog.yaml)

## Objective

Perform one bounded, independent acceptance audit of the completed core lab. Reconstruct the acceptance case from authoritative requirements, source, tests, documentation, and freshly executed evidence rather than treating `docs/STATE.md`, `docs/WORKLOG.md`, prior task plans, or previous PASS claims as proof.

The audit may report correctness, reproducibility, documentation, or safety findings. It does not fix findings, change runtime behavior, reopen a completed product task, add a Possible extension, or silently strengthen the delivery semantics. If a finding requires work, implementation begins only after a separate bounded maintenance task has been added to the backlog and selected explicitly.

The audit result will be recorded in `docs/audits/BI-090.md`. Generated logs may be retained only below ignored `artifacts/audit/`; they are supporting evidence, not project state.

## Independence and mutation boundary

Independence means that the reviewer:

- derives a fresh requirement checklist directly from the specification, accepted ADRs, repository policy, and BI-010 through BI-080 backlog acceptance criteria;
- follows requirements to implementation and tests, then reproduces critical evidence with new commands;
- treats existing state, plans, worklog entries, and generated reports as claims to corroborate, not as acceptance evidence by themselves;
- records the exact Git revision, working-tree status, audited file set, tool versions, and command outcomes;
- distinguishes a clean committed checkout from a working-tree export that includes tracked modifications or untracked files;
- does not reuse mutable developer services or data as the sole basis for a passing result.

During BI-090, permitted repository changes are limited to:

- `docs/audits/BI-090.md`;
- status/handoff updates in `tasks/backlog.yaml`, `docs/STATE.md`, and append-only `docs/WORKLOG.md`;
- the BI-090 plan status after the audit is complete;
- creation of one separately scoped backlog maintenance task when an actionable finding requires follow-up.

The audit must not edit `src/`, `mock_api/`, `postgres/`, `scripts/`, tests, fixtures, Compose configuration, dependencies, lockfiles, contracts, README behavior, or accepted ADRs. Runtime checks may create ignored artifacts and isolated Docker/S3/PostgreSQL state, but cleanup must be bounded and select only audit-owned resources. An observed failure is evidence; it is not repaired inside the audit.

## Baseline and reproducibility contract

Before judging behavior, capture:

```text
UTC audit start time
reviewer/session identifier
Git HEAD commit
branch
full git status --short
tracked and unignored file inventory used by the audit
Python, uv, Docker, and Docker Compose versions
accepted specification and ADR paths
```

The report must state one of these baseline classes:

- `clean_commit`: the audited tree exactly matches a commit and can be checked out independently;
- `dirty_worktree`: tracked modifications and/or untracked source files are part of the audited tree;
- `blocked_baseline`: the source set cannot be enumerated safely or reproduced.

A working-tree export from `git ls-files --cached --others --exclude-standard` may test file closure, but it must not be described as a clean clone or clean committed checkout. If the completed behavior depends on files absent from `HEAD`, record an actionable reproducibility finding with exact paths and commands. Do not commit, stash, reset, or clean the developer worktree during the audit.

All live acceptance runs use a unique audit project name, bucket, loopback ports, owner-only ignored environment file, and artifact directory. Capture protected default-project fingerprints before and after. Cleanup may destroy only the exact generated audit project through the existing confirmed path. A cleanup failure remains a finding or blocked check; it is never hidden by broad Docker deletion.

## Audit report contract

Create `docs/audits/BI-090.md` with these fixed sections:

1. **Verdict** — `no_findings`, `findings_recorded`, or `blocked`, plus a one-paragraph basis.
2. **Audited baseline** — provenance fields and baseline class.
3. **Scope and exclusions** — core scope only; Possible extensions explicitly excluded.
4. **Findings** — ordered by severity and identifier, or the exact statement “No actionable findings identified.”
5. **Requirement traceability** — every in-scope specification/ADR/backlog requirement mapped to implementation, tests, documentation, and fresh evidence.
6. **Validation evidence** — command, start/end time, exit code, PASS/FAIL/NOT RUN, and artifact-relative log path where applicable.
7. **Residual limitations** — only intentional documented trade-offs that are not findings.
8. **Follow-up** — the separately created maintenance task ID, or `none`.

Every finding uses this schema:

```text
ID: BI-090-FNN
Severity: critical | high | medium | low
Category: correctness | reproducibility | documentation | safety
Authority: exact specification, ADR, backlog, or repository-policy clause
Evidence: file:line references and/or exact bounded reproduction command
Observed result: concrete behavior, state, or command output
Expected result: authoritative requirement
Impact: why acceptance, recovery, safety, or reproducibility is affected
Recommended boundary: smallest verifiable repair, without implementing it
Acceptance impact: blocking | non-blocking
```

Severity meanings are fixed:

- `critical`: demonstrated data loss, secret exposure, destructive cross-project action, or corruption of immutable evidence;
- `high`: an in-scope specification, accepted ADR, or reliability invariant is materially violated;
- `medium`: a required failure path, reproducibility guarantee, operator contract, or acceptance claim lacks correct implementation/evidence;
- `low`: a concrete documentation or safety defect with a bounded correction and real operator impact.

Do not record style preferences, speculative production features, optional hardening, or Possible extensions as findings. Do not downgrade a failed mandatory check to an observation. Duplicate symptoms with one root cause become one finding with all affected evidence.

## Requirement and evidence matrix

The audit report expands this matrix to individual requirements; no row may be accepted solely by citing a prior plan or worklog entry.

| Area | Required review | Fresh evidence minimum |

Text search may locate candidates, but each conclusion must be confirmed in the enclosing implementation and test behavior.

## Execution slices

### Slice 1 — Freeze baseline and build traceability

1. Capture the provenance fields and classify the baseline before starting services.
2. Read the specification through `Deliberate trade-offs`, both accepted ADRs, all backlog acceptance criteria, and current contracts/operator documentation.
3. Build the report’s requirement rows with authoritative citations; mark evidence initially `unverified`.
4. Compare `HEAD` with the audited working tree and identify any implementation, tests, fixtures, or docs unavailable from a clean checkout.
5. Stop as `blocked` if the source set is unsafe or requirements cannot be enumerated; otherwise continue without modifying product files.

### Slice 2 — Adversarial static review

1. Trace each requirement through its production implementation, test coverage, and operator documentation.
2. Inspect module boundaries, import-time behavior, retry/deadline loops, stream/spool ownership, exception classification, and cleanup paths.
3. Inspect deterministic identity/key/checksum/manifest relationships and every raw-before-manifest or copy/verify/delete boundary.
4. Search for forbidden or misleading patterns—credentials, floating images, `SELECT *`, whole-result reads, direct domain `boto3` use, ETag-as-SHA, unbounded waits/retries, atomic-rename language, exactly-once claims—and review every candidate in context.
5. Record candidate findings only after tying them to an authority and reproducible evidence.

### Slice 3 — Fresh bounded validation

Run the validation matrix below from the captured baseline. Live checks use isolated audit-owned configuration and services. The reviewer records first failures exactly; retries are allowed only after documenting the failed run, and both results remain in the report.

For critical claims, inspect produced state rather than accepting an exit code alone: exact object keys, streamed SHA-256, manifest linkage/status, absent forbidden dispositions, duplicate replay inventory, snapshot schema/order/bounds, retained malformed/rejected bytes, and protected-resource fingerprints.

### Slice 4 — Findings, follow-up, and closeout

1. Resolve each candidate as a supported finding or remove it; do not leave speculative items.
2. Complete every traceability row with PASS, FAIL, BLOCKED, or NOT RUN and exact evidence.
3. If no actionable finding exists, state that explicitly and set follow-up to `none`.
4. If repair is required, add a separately identified bounded maintenance task with one coherent failure boundary, dependency on BI-090, exact acceptance criteria, and no implementation; do not reopen BI-010–BI-080 or edit product code.
5. Finalize the audit report, append the worklog, and synchronize backlog/state. Task closeout must not invent a product feature merely to populate the next-task field; any next active task must be explicitly justified by an audit finding or separately authorized maintenance request.

## Follow-up decision rules

- Do not implement a finding during BI-090.
- One maintenance task must represent one coherent root cause and have bounded tests/acceptance. If findings are unrelated, create separate tasks and select exactly one next atomic task; do not bundle them merely to close the audit.
- A finding that changes Garage, manifest/object-key contracts, file atomicity, coordination, or claimed delivery semantics requires an ADR task before implementation.
- A failed mandatory acceptance check is not waived because previous evidence passed.
- A blocked environment check remains visible; it may justify a bounded reproducibility-maintenance task.
- Completed core tasks remain `done`; follow-up uses a new maintenance task and references the finding ID.

## Acceptance criteria for BI-090

BI-090 is complete only when:

- the exact audited baseline and clean-commit/dirty-worktree distinction are recorded;
- every in-scope specification requirement, accepted ADR obligation, and backlog acceptance criterion has traceable implementation, test, documentation, and fresh-evidence status;
- prioritized actionable findings include exact authority and evidence, or the report explicitly records none;
- all commands are reported as PASS/FAIL/NOT RUN/BLOCKED without hiding first failures;
- runtime audit resources are bounded, isolated, and cleaned without changing protected state;
- no product/runtime/test/dependency/ADR change is mixed into the audit;
- every required repair is represented by a bounded maintenance task before implementation;
- backlog, state, plan status, and append-only worklog are synchronized without implicitly reopening completed scope.

## Non-goals and risks

- No code fix, refactor, dependency update, ADR replacement, feature, Possible extension, performance project, production-hardening program, or new delivery guarantee.
- Passing tests alone do not prove requirement completeness; static traceability and retained-state inspection remain required.
- Existing worklog/state claims may be stale or self-authored and are never sufficient evidence.
- A dirty working tree can pass an export harness while a checkout of `HEAD` cannot reproduce the product; the report must preserve this distinction.
- Docker/image/cache availability may block live evidence. Record the block and bounded diagnostics; do not use public services or unbounded retries.
- The audit cannot prove concurrent-writer safety, Garage versioning, atomic S3 rename, or exactly-once delivery because those are explicit non-contracts.

During execution, any library-specific finding must be checked against current version-matched documentation before it is finalized; the report cites that source without changing dependencies.
