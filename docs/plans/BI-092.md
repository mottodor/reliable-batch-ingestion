# BI-092 implementation plan — persist and reconcile REST logical-run manifests

Status: complete; all five slices finished and BI-093 selected as the next atomic task

Dependencies: `BI-091` is complete and [ADR 0003](../adr/0003-persist-rest-logical-run-manifest.md) is accepted

Authority: [product specification](../specification/batch-ingestion.md), [ADR 0001](../adr/0001-use-garage-for-s3-compatible-storage.md), [ADR 0003](../adr/0003-persist-rest-logical-run-manifest.md), [core contracts](../contracts/core-contracts.md), [storage contract](../contracts/storage-contract.md), [REST ingestion contract](../ingestion/api-ingestion.md), and [`BI-090-F02`](../audits/BI-090.md#bi-090-f02)

## Objective

Close `BI-090-F02` by implementing the exact ADR 0003 completion contract for REST ingestion. A successful logical API batch with `N` pages must leave exactly `N` immutable raw page objects, the same `N` schema-version-1 page manifests, and one immutable `api_logical_run_manifest` at the deterministic batch key. The aggregate must be fully reconciled before the service emits terminal success or its final `RunSummary`.

The change must upgrade legacy page-only batches during ordinary replay, preserve mixed page-manifest `run_id` values, retain existing metric meanings, and keep backfill on the existing fail-fast single-date primitive. It must use exact derived keys and streamed SHA-256 evidence rather than `ETag` or prefix listing.

The delivery claim remains deterministic keys, immutable idempotent writes, and safe sequential redelivery. BI-092 does not introduce exactly-once delivery, concurrent-writer safety, a mutable checkpoint, or durable failed-attempt history.

## Current implementation seam

The current REST service already provides the required page-level foundation:

- `api_page_identity()` and `derive_batch_id()` establish one logical identity per source/date/resource path/page size;
- `ingest_api_date()` fetches and validates strict sequential pagination, writes raw bytes before parsing, and reconciles each exact raw/page-manifest pair;
- `S3Storage` streams actual bytes for immutable writes and page-pair reconciliation and exposes bounded exact-key `download_spooled()` reads;
- completed page manifests may correctly retain different physical `run_id` values after recovery;
- the success event and final summary are emitted only after the page loop, which provides the insertion point for aggregate reconciliation;
- `ingest_api_backfill()` already delegates every date to `ingest_api_date()` and stops on the first failure;
- `DemoInventoryVerifier` verifies page payloads/manifests and exact prefixes but currently has no aggregate concept.

The missing behavior is a separate strict aggregate model/key/parser, exact aggregate/page-evidence inspection, a complete reconciliation state machine, aggregate publication between the page loop and success output, and readers/docs that require one aggregate for each successful API batch.

## Contracts that must not change

- Raw page keys, page-manifest keys, `BatchIdentity`, `batch_id`, page-manifest schema version 1, and all existing stored page bytes remain unchanged.
- `Manifest`, `Manifest.from_json()`, and `manifest_key_for()` continue to represent exactly one raw payload. They must not parse or derive the aggregate.
- The aggregate has no synthetic raw payload and does not increase `bytes_written`.
- `duplicate_count` continues to count reused successful page pairs, not aggregate reuse.
- Existing event and `RunSummary` field shapes remain unchanged. New stable aggregate failure codes may populate the existing nullable `error_code` field.
- Normal ingestion continues to fetch and validate source pages. A complete aggregate is durable completion evidence, not an offline source substitute.
- Failed/partial attempts do not write an aggregate. Existing failed page manifests remain terminal.
- Storage access remains through `S3Storage` and the standard S3 API. Domain code must not import `boto3`, inspect `ETag`, administer Garage, or use prefix listing as a completion oracle.
- No network, S3 client, clock, or environment access may occur at import time.
- Raw backend S3 exceptions outside the aggregate-specific state machine remain BI-093 scope; BI-092 must not broaden into cross-source terminal-summary normalization.

## Module and ownership plan

Add two API-owned modules and reuse the shared storage boundary:

- `src/batch_ingestion/api/logical_manifest.py`
  - aggregate constants and exact field sets;
  - `ApiLogicalRunPage` and `ApiLogicalRunManifest` frozen typed models;
  - deterministic `api_logical_run_manifest_key()` helper;
  - canonical UTF-8 serializer and strict bytes parser;
  - descriptor resolution, identity rederivation, key/count/page-linkage validation.
- `src/batch_ingestion/api/logical_run.py`
  - exact page-evidence collection from shared storage reads/results;
  - aggregate observation and reconciliation classifications;
  - immutable publication and bounded uncertain-write convergence;
  - typed API-specific failures mapped by the REST service.

Modify, but do not duplicate, these existing boundaries:

- `src/batch_ingestion/api/service.py` orchestrates preflight, page traversal, eligibility, publication, post-write verification, output ordering, and unchanged metrics.
- `src/batch_ingestion/storage.py` is changed only if a small generic exact-key observation surface is needed beyond `download_spooled()`; any addition must remain source-neutral, stream actual bytes, enforce caller-provided limits, close response bodies, and preserve existing callers.
- `scripts/demo_inventory.py` derives and requires the aggregate key for successful API records and includes its actual bytes in exact inventory evidence; failed API evidence must not imply completion.
- Existing API unit/integration/backfill/demo tests are extended, with focused new test modules for the pure aggregate contract and reconciliation state machine.

Do not place the new model in `manifests.py`: that module owns the one-payload schema shared by API, file, and snapshot ingestion, while ADR 0003 requires an independent API-specific schema/version namespace.

## Fixed implementation design

### 1. Aggregate identity, key, and canonical bytes

`api_logical_run_manifest_key(identity)` accepts only `SourceType.API`, derives `batch_id` from the supplied canonical identity, and returns exactly:

```text
manifests/api/{source_name}/source_date={YYYY-MM-DD}/batch_id={batch_id}/logical-run.manifest.json
```

It does not call `manifest_key_for()` and accepts no caller-supplied `run_id`, attempt, or unverified batch ID. Unit tests lock both key examples from ADR 0003.

`ApiLogicalRunManifest` and `ApiLogicalRunPage` enforce every exact field and type from ADR 0003. In particular:

- booleans are rejected wherever integers are required;
- `manifest_type`, `schema_version`, `source_type`, `status`, canonical date/timestamp/ID forms, exact identity-parameter keys, page-size range, and allow-listed resource path are fixed;
- the descriptor is resolved from `source_name`; a fresh `BatchIdentity` is built from `source_date`, `resource-path`, and `page-size`; `batch_id` is rederived rather than trusted;
- page numbers are exactly `1..page_count`, ordered, unique, gap-free, and no greater than 9,999;
- every raw and page-manifest key is independently rederived for that identity/page number;
- `page_count == len(pages)` and also equals `max(1, ceil(record_count / page_size))` under the existing pagination rules;
- every non-final page has `record_count == page_size`; the final page has the exact remaining count, including zero for the one-page empty result;
- page-entry counts sum to aggregate `record_count`, which remains within `0..999900`;
- payload lengths fit the ADR range and all checksums are 64 lowercase hexadecimal characters.

Serialization returns compact UTF-8 bytes with sorted keys at every level, no BOM/newline/ASCII forcing, canonical integer/timestamp forms, and pages in validated order. The generated bytes are rejected before publication if they exceed 8,388,608 bytes.

Parsing operates on bytes, not an already-decoded dictionary. The exact-key reader first rejects a declared length over 8 MiB, stops if streamed actual bytes exceed 8 MiB, and checks declared/actual equality. The parser independently rejects a byte string over 8 MiB, then must:

1. decode strict UTF-8 and reject BOM/trailing data;
2. detect duplicate member names at every object level with an `object_pairs_hook`-style parser path;
3. reject non-object roots, missing/unknown members, unsupported type/version, and wrong JSON types;
4. build and fully validate the typed model;
5. reserialize it and require byte-for-byte equality with the input, making noncanonical JSON invalid.

The 64 KiB existing page-manifest bound remains unchanged. Tests build the full 9,999-entry longer-source case and prove its canonical output remains inside 8 MiB without weakening the fixed limit.

### 2. Exact page evidence

One successful page contributes a frozen evidence record only after its raw/page-manifest pair is complete and independently verified. The record contains exactly the aggregate page fields and is constructed from actual storage observations:

- raw `StoredObject` length and streamed SHA-256, not response headers or `ETag`;
- exact page-manifest bytes read under the 64 KiB bound, their streamed SHA-256, and strict schema-version-1 parsing;
- page-manifest linkage to the exact raw key, content length/checksum/type, source/date/batch, and terminal `succeeded` status;
- validated item count from the current strict source page envelope.

For a newly written page, the immutable-write verification result may supply the raw observation. For a reused page, the page reconciliation result supplies it. Exact page-manifest bytes are read through the shared bounded exact-key helper so their checksum includes the original `run_id`, `extracted_at`, and `attempt`. Mixed page-manifest `run_id` values are explicitly allowed and are never normalized.

No aggregate logic accepts a page key because it merely shares a prefix. Every key is derived from identity plus page number, and every referenced object is read by exact key.

### 3. Two-phase aggregate reconciliation

The service performs aggregate reconciliation in two phases so an invalid present completion claim cannot be silently healed.

**Preflight before HTTP or storage mutation:**

1. derive the one aggregate key from the logical identity;
2. inspect that exact key with both declared and actual 8 MiB limits;
3. if absent, record `absent` and continue through the normal page flow;
4. if present, parse canonical bytes, require the key/document identity to match, then stream and verify every exact referenced raw/page-manifest object;
5. classify malformed/oversized/noncanonical/duplicate-keyed/unsupported content as `corrupt`, identity/key/count/checksum/status mismatch as `conflicting`, and a missing referenced object as `orphaned`;
6. stop visibly on corrupt/conflicting/orphaned state without fetching or writing source evidence;
7. retain a valid `complete` aggregate and its original bytes, checksum, `completion_run_id`, and `completed_at`, then still run normal source fetching/validation.

The preflight mutation barrier is important: when a present aggregate references a missing object, normal page ingestion must not recreate that object and accidentally legitimize an orphaned completion claim.

**Completion after the page loop:**

- `absent` plus a partial/interrupted traversal remains `incomplete`; no aggregate is built or written.
- `absent` plus a terminal failed page remains `failed`; the existing page failure is re-surfaced and no aggregate is written.
- `absent` plus every verified page pair and final pagination totals becomes `eligible`; one model is built with the current `run_id` and injected UTC completion time.
- `complete` requires the newly observed source traversal and page evidence to match the already validated aggregate exactly except that the current physical `run_id` is irrelevant. The stored aggregate remains unchanged.
- after creation or uncertain-write recovery, the service re-reads and fully reconciles the aggregate and all referenced evidence as `complete` before success output.

Expose an internal enum/result carrying `absent`, `incomplete`, `failed`, `eligible`, `complete`, `corrupt`, `conflicting`, `orphaned`, and `uncertain_write` outcomes so every ADR row is table-tested. Only `eligible` may invoke publication; only `complete` may permit terminal success.

### 4. Immutable publication and uncertain writes

Freeze the valid canonical aggregate bytes, length, SHA-256, key, `completion_run_id`, and `completed_at` before the first write. Call `S3Storage.write_immutable()` with `application/json` and do not regenerate bytes between attempts.

Uncertain publication is bounded to at most two immutable-write invocations in one physical run, with exact inspection after an uncertain exception:

- if the key contains the byte-identical frozen object and full evidence reconciliation is complete, accept it;
- if the key is absent, rewind and retry the same frozen bytes once;
- after a second uncertain result, inspect once more and accept only the same fully valid bytes; an absent key remains a visible uncertain-write failure;
- any other present bytes are a conflict and remain untouched.

A later ordinary rerun differs from same-attempt uncertain recovery: it may accept any fully valid complete aggregate and must preserve that object's first `completion_run_id` and `completed_at`. A different valid object appearing during the current uncertain-write window is treated as a conflict because concurrent writers are unsupported.

There is no delete, overwrite, mutable status change, conditional-put correctness claim, or unbounded retry loop.

### 5. Service ordering, outputs, and errors

`ingest_api_date()` gains these ordering assertions:

```text
aggregate preflight
-> page fetch/raw/page-manifest processing
-> aggregate eligibility/reuse/publication
-> full aggregate completion verification
-> terminal succeeded api_ingestion event
-> final RunSummary
```

On page/HTTP failure, the existing failure path runs and no aggregate publication is attempted. On an aggregate contract failure, the existing event/summary shapes are retained with stable codes:

```text
logical_run_manifest_corrupt
logical_run_manifest_conflict
logical_run_manifest_orphaned
logical_run_manifest_write_uncertain
```

These codes distinguish retained aggregate evidence that requires investigation. Existing `storage_error` behavior remains for ordinary storage failures; BI-093 separately addresses raw backend exceptions that currently bypass terminal output.

`ApiIngestionResult` adds the verified aggregate key as a separate field. Existing `payload_keys`, `manifest_keys`, `bytes_written`, and `duplicate_count` retain page-only meanings. A replay with a complete aggregate and mixed page runs returns the stored completion key while preserving aggregate/page bytes and completion facts.

Injected `utc_now`, run-ID factory, storage fake, and event sink keep publication order and first-publication facts deterministic in unit tests.

### 6. Backfill, exact inventory, and demos

Backfill receives no new loop or storage format. Because each date still calls `ingest_api_date()`, that date cannot succeed until its aggregate is complete; the existing fail-fast behavior then stops on any aggregate failure.

For exact demo inventory:

- derive the aggregate key from a successful API record's exact identity prefix;
- require the manifest prefix to contain exactly the page-manifest keys plus `logical-run.manifest.json`;
- read the aggregate under the 8 MiB bound, parse it with the production strict parser, and verify every page link/checksum against already streamed inventory evidence;
- include aggregate bytes in `DemoInventoryEvidence.objects` and in the manifest count while leaving raw count unchanged;
- require no aggregate for a terminal failed API batch;
- update exact-count assertions and clean-export expectations from measured implemented inventory rather than retaining pre-BI-092 page-only counts.

Listing remains useful only to assert the demo's exact expected prefix inventory. Production completion reconciliation uses exact derived keys and never listing.

## Non-goals and risks

- No BI-093 backend-failure summary normalization, BI-094 slow-trickle deadline repair, BI-095 preflight repair, or BI-096 clean-commit attestation.
- No change to page-manifest schema version 1, raw/page keys, source descriptors, pagination envelope, CLI syntax, configuration variables, or runtime dependencies.
- No eager bucket-wide migration. Legacy batches gain an aggregate only through normal replay of the same source/date identity.
- No failed aggregate, mutable aggregate, per-attempt aggregate, attempt history, synthetic payload, prefix-based completion inference, or automatic cleanup of bad evidence.
- No concurrent-writer safety. Same-attempt uncertain recovery deliberately rejects different present bytes even if another writer might have produced a structurally valid document.
- A corrupt/conflicting/orphaned immutable aggregate blocks automatic completion and requires operator investigation; silently replacing it would violate ADR 0003.
- Aggregate parsing may hold at most the explicit 8 MiB document in memory. Raw pages remain streamed/bounded, and the full multi-page source payload is never accumulated.
- Existing local demo-state files may encode page-only inventory assumptions; tests/documentation must provide an explicit rerun path rather than silently treating stale state as aggregate-complete.

## Documentation basis

Planning checked current Context7 documentation for `/boto/boto3`. The official S3 examples confirm that `get_object()` exposes a streaming file-like `Body` read through `.read()`, while S3 response metadata includes `ContentLength` and object metadata. BI-092 continues to hide those library details behind `S3Storage`, closes streamed bodies, verifies declared and actual lengths, and computes SHA-256 from actual bytes. No new runtime dependency is required.
